# 决策反驳、支持理由与证据裁决

## 先站在反方

你目前最危险的前提是：“Skill 已经有效，所以完整搬成客户端，再优化一下，就能得到稳定长篇写作产品。”实际证据只支持前半句中的一部分：这套 Skill 有具体创作方法和档案约定。它还没有提供经过验证的运行内核、事务系统、严格数据契约、长期质量实验或商业需求。

| 隐含前提 | 反证或缺口 | 不修正会付出的代价 |
| --- | --- | --- |
| 写进 Skill 的要求，AI 就会稳定执行 | 校验器允许空字段和否定同步标记；提示词不等于执行约束 | 界面显示完成，后续数十章继承错误 |
| 完整流程等于全部自动化 | 你已要求每阶段确认；作者判断是流程的一部分 | 偷跑消耗费用；或确认过多导致工具比手工作业更慢 |
| 能写三章，就能支撑 300 万字 | 样书只到 003；三位章节正则甚至漏掉 1000 | 后期才发现编号、上下文、迁移和恢复不能扩展 |
| 所有主流厂商加中转都可无差别接入 | 协议、流式、工具回传、模型参数、计费信息不同 | 最后变成持续维护大量兼容分支 |
| 模型评分高就是更好 | 第一章评分分项合计 88，报告写 89；文学评分本身也主观 | 把错误分数当决策依据，越修越偏 |
| 做成 Codex 外观就具有 Codex 执行能力 | 任务恢复、权限、工具结果、状态持久化都是独立工程 | 前端完成大半，核心仍不可用 |
| 现成开源项目能直接拿来收费 | PlotPilot 附加 Commons Clause；另两个参考项目为 AGPL | 后期大面积替换代码或改变分发方式 |
| 以后再想收费，不影响现在设计 | 已经影响第三方代码复用、授权设计和数据可携带性 | 形成难逆转的技术与许可证耦合 |
| 功能越多，价值越大 | 封面、音视频、支付、社区均未证明能改善核心写作 | 挤占正文连续性、备份和修订闭环投入 |
| 新建客户端必然优于已有网站 | `D:\aiwangzhan` 已有协议层、工具循环、Codex 桥接 | 重写重复逻辑；也可能将服务器复杂度全部搬入桌面 |

PlotPilot 许可证中的收费限制需要在计划复用代码前解决；“安装包免费”本身不足以消除其对相关收费服务的影响。这里是基于条款的工程风险判断，具体商业模式下的权利边界需在分发前确认。[固定版本许可证](https://github.com/shenminglinyi/PlotPilot/blob/cbd260ba7b5fe35e53f528937c4a240fb67ea2dc/LICENSE)

AGPL 与这个限制不能混为一谈；它不是简单禁止收费。对另两个 AGPL 参考项目，需要确认实际复用、分发与源码义务是否符合计划，不能从“免费安装包”推导出可以任意闭源复用。[Linetta 的许可说明](https://github.com/devlikebear/linetta/blob/34cf973d8ca15f32d5473181f6a381d0835596ec/LICENSE-NOTICE.md)

## 遗漏信息

预算、可用时间、维护人、目标机器资源、收费项目、精确供应商与模型版本、联网范围、是否出版平台直发、备份容灾要求，尚未全部确定。它们分别影响开发规模、安装包形态、兼容范围、权限模型、恢复策略与持续成本。第 10 篇逐项列出，不能用“全部都要”替代这些约束。

还缺一项关键业务证据：当前手动使用 Skill 时，最耗时、最容易错、最想省掉的是哪一步。现在只能根据源码识别工程缺陷，不能推断所有作者的真实痛点。你愿意审核所有阶段，不等于其他作者也愿意；个人可用和公开分发应分别验收。

## 难以逆转的成本

| 成本 | 什么时候形成 | 控制办法 |
| --- | --- | --- |
| 正文与设定污染 | 旧事实被更新为“当前真相”且找不到来源 | 正文版本、事实来源、修订失效链和提交前快照优先 |
| 格式锁定 | 只存私有数据库或富文本内部格式 | Markdown 为作品事实来源；导出不依赖付费许可 |
| 数据迁移债务 | 一个字段几种语义，升级靠正则替换全文 | 版本化 schema；备份、预览、往返保留、失败恢复 |
| 许可证耦合 | 直接大量复制受限制项目，再叠加收费能力 | 借鉴设计；复用前单独决定许可证策略 |
| 供应商耦合 | 工具事件与某一家响应结构混入业务层 | 协议适配器；保存原生不透明块；统一业务事件 |
| 公开分发信誉 | 作者把唯一底稿交给软件 | 恢复演练和外部编辑冲突验收后再扩大使用 |

## 机会成本

自己开发客户端的时间，本来可以用来写书、验证题材、修正 Skill、研究读者反馈。没有投入上限时，架构调研和功能清单会不断延长，却没有新增可发表正文。更复杂的多智能体、知识图谱或插件市场，也可能只增加耗时与 API 成本。

现有网站代码提供了一条可验证的复用路线；完全忽略它会重复投入。反过来，把租户、组织权限、Redis 调度、计费结算、脚本平台全部打包成本地程序，也会为个人写作承担不必要运维。应比较的是“哪些业务契约可以复用”，不是“整站重写”和“整站搬家”二选一。

## 最坏但具体的失败情景

你在外部编辑器修订第 15 章，客户端没有识别影响。它读取旧角色状态，生成 16—30 章；章后总结把新错误写回记忆。你中断程序，重启后它重试已经收费但未返回完整结果的调用，同时将已确认正文覆盖。没有可恢复版本时，损失不仅是 API 钱，还包括找回正确故事线的人工劳动。

这种情景由多个已存在的薄弱环节组合而来，并非声称当前文件已经发生了这些损失。它决定了应优先验证哈希冲突、候选与正式版本、未知调用状态、崩溃恢复，而不是优先增加页面。

## 可能影响判断的认知偏差

以下是决策中需要防范的倾向，不能据此诊断你的心理状态。

- 完美化目标：以“所有功能甚至更好”为完成标准，却没有有限验收边界，会持续推迟可用版本。
- 自动化偏差：更整齐的面板、评分和执行日志，容易让人高估结果正确性。
- 沉没成本：已经收集大量资料、已有网站源码，可能让人觉得必须做成大型产品才能回本。
- 规划谬误：低估兼容、迁移、安装、恢复和长期维护，容易只按页面数量估价。
- 确认偏差：只看同类项目 README、星数和演示，没有运行自己的边界用例。

## 切换到支持视角

成立的核心理由是具体的：

1. 原 Skill 的阶段、文件、批次和章后更新已经足够明确，可以转成可追溯业务规则，不必从零发明写作方法。
2. 个人 Windows、BYOK、本地 Markdown 的范围，比多人云平台更容易形成完整闭环。
3. 你愿意保留人工阶段审核。这允许软件负责查漏、执行和记录，作者负责审美与故事选择，降低错误直接成为正式正文的概率。
4. 软件在计数、字段检查、索引、版本、文件差异、批次边界上具有明确优势。这些改善可测量，不依赖模型“更聪明”。
5. 有可导入的 33 文件样书，有已复现的错误样例，还有网站协议层作参考，可以直接构建回归用例。
6. GitHub 已有 Electron、Tauri、文件型工具循环等不同实现，证明这些组件组合具有可行路线；它们并未证明你的产品质量或商业价值。

## 中立比较后，哪边占优势

| 被评估的决定 | 当前判断 | 关键证据 | 置信度 |
| --- | --- | --- | --- |
| 做一个自己能用、保留全部 Skill 规则的 Windows 客户端 | 支持占优势 | 范围相对明确，模板和样书可用，用户接受审核 | 中高 |
| 现在承诺一次做完并且文学质量全面更好 | 反对明显占优势 | 没有预算、工期、质量基线；长篇和恢复未验证 | 高 |
| 直接基于 PlotPilot 大量复制后做收费功能 | 反对占优势 | 附加许可限制，关键探针有缺陷，三种运行时 | 高 |
| 借鉴其分层记忆、上下文预算和流水线 | 支持占优势 | 问题分解适用，但需独立实现和验证 | 中高 |
| 因为像 Codex 就强制所有供应商走 Responses | 反对占优势 | 用户希望多协议；本机已有四类协议 | 高 |
| 在可靠写作闭环前建立支付、社区、插件市场 | 反对占优势 | 收费项未定，增加的成本不能支撑当前目标 | 高 |

最大未知是：经过全部人工确认、记忆审核和修订后，客户端能否真正减少你每章的总劳动。最大技术风险是：如何让跨文件事实、运行状态与用户批准始终指向同一版本。

## 什么条件会让结论反转

支持扩大投入的条件：在真实目标机器和实际中转端点上，完成一条从导入到第 31 章的闭环；修订早期章节后能准确标出影响；注入崩溃和外部修改后没有静默覆盖；在相同模型与预算下盲评不劣于原流程，而且总修稿时间下降；预算、维护人与收费边界有明确约束。

削弱支持的条件：你无法接受必要的结果审核；目标模型持续不能可靠调用工具且不愿缩小兼容承诺；必须在很短期限内同时交付出版平台直发、支付、音视频、云同步；数据恢复仍依赖手工找文件；客户端与原 Skill 同条件比较没有节省时间。

如果后续确认只用可稳定支持 Responses 的少数模型，并且现有网站 Codex 桥接通过桌面样机测试，内核推荐可以从自建工具循环转为 Codex App Server。若团队已有强 Rust 能力且安装体积是硬指标，桌面壳推荐可以从 Electron 转为 Tauri。这些是有证据触发的变更，不是现在为所有可能性同时开发。
