## 3. 工程推荐，尚非用户指定

| 推荐 | 理由 | 允许反转的证据 |
| --- | --- | --- |
| Electron/React/TS | 单主语言，适合编辑、文件和事件，减少多运行时维护 | 团队 Rust 优势、体积硬指标或样机性能证据 |
| 自建多协议 Runner | 用户模型自设，四协议需求与本机参考明确 | Responses 端点统一且 App Server 桥接样机显著降低成本 |
| SQLite 管理记录、MD 保存作品 | 与外部编辑要求一致，同时保存不能重建的运行与批准 | 用户后续明确改成数据库主格式，此时需重审需求 |
| 候选/正式分离与可恢复事务 | 防止错稿和半提交，被源码问题直接支持 | 实现方案可换，可靠性约束不能删除 |
| 语义疑点交作者审阅 | 模型不能证明所有连续性和审美判断 | 有经过验证的特定规则可提升为确定性检查 |
| 暂不建立收费后台、云同步、插件市场 | 收费未定，当前个人写作优先 | 用户补充明确商业或协作需求 |
| 三层为同一套资料的不同视图，MD 为正式资料、SQLite 为控制记录和索引 | 防止多份角色卡/事实副本分叉；沿用 D08/D19 | 样机证明另一实现更易恢复且不改变可读文件与确认要求 |
| 精确实体/关系/全文检索先行，可选向量补充 | 关键限制需要可解释召回；减少初始服务依赖 | 同条件评测证明语义漏召回被向量显著改善，且费用可接受 |
| 上章完整正文＋最近三章变化摘要作为近期窗口初值 | 只是待评测的可调默认；当前批次必读与长期未解决事项不受窗口截断 | 实际上下文预算、连贯性和作者修稿时间显示应扩大或缩小 |
| 必读资料压缩须先验收覆盖，超限不得静默生成 | 原 Skill 等价性需要证据；分页不等于无限上下文 | 覆盖评测通过后可启用投影；不能取消缺口提示和来源回查 |

本轮未要求用户再次决定预算、工期、收费、模型型号或备份目录；这些既有未决状态继续有效。三层的业务目标已经确认，具体窗口、检索上限、阈值、保留数量属于待样机验证的工程提案，不能写成用户已指定。

## 4. 决策变更应怎样记录

每次变更保存：谁提出、时间、旧决定、新决定、原因、受影响 REQ、文件格式/迁移风险、需重跑验收。规则改变不能静默让旧结果继续显示合格。

后续必须提问的触发点：供应商只有某种协议但要求完整 Agent；新增收费或复用受限制代码；导入需要舍弃复杂文档内容；改变已规划批次范围；涉及系统目录/全局安装/删除的具体执行；需要跨作品或云同步。普通实现方法、内部变量名和可逆格式排版不需要假装是产品不确定性反复询问作者。
