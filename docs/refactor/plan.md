# 2. 已决定的目标架构

## 2.1 分层与依赖方向

```text
React UI
  → Typed Client Contract
  → Electron preload / main
  → Application Services
       ├─ Project Lifecycle / Task Scheduler / Approval Service
       ├─ Agent Runtime Port
       │    ├─ Legacy Executor Adapter（首先接入）
       │    └─ Pi Executor Adapter（通过准入后启用）
       ├─ Model Gateway → 现有四类 Provider Adapter
       ├─ Tool Gateway → 受控的版本化读、检索、草稿、候选
       ├─ Context Builder → 来源清单、工作集、检索、派生摘要
       └─ Project Commit Kernel
            → SQLite / Object Store / Transaction Journal / File Outbox
```

主进程负责系统能力、可信密钥托管、IPC 来源验证和 worker 监管。业务进程继续是可信本地业务边界；本轮不额外建立第三方通用插件宿主。

代理核心只依赖客户端定义的执行接口和受控能力。它不能导入 SQLite 连接、正式提交实现、Electron API 或任意真实项目写入函数。界面不能导入代理供应商类型。组装与依赖注入集中在组合入口，不使用全局可修改 Service Locator。

## 2.2 权威职责分配

| 事项 | 唯一控制者 | 不得代替它的机制 |
|---|---|---|
| 正式内容与项目修订 | Project Commit Kernel | 模型回复、第三方“任务完成”事件 |
| 候选是否批准 | Approval Service + 可信客户端命令 | 模型生成的 `approved: true`、工具参数 |
| Run 生命周期与恢复策略 | Task Application Service | 多个 runner 自行赋值 |
| 单次代理循环如何推进 | 被选中的一个 Executor Adapter | 同时叠加两套代理循环 |
| 远端请求计费、尝试、重试许可 | Model Gateway | SDK 隐藏重试、压缩函数自行 fetch |
| 工具权限、去重与执行记录 | Tool Gateway | 执行器绕过网关调用 handler |
| 正式文件物化 | Outbox Worker | 代理直接写最终文件 |
| 进程重启与关闭 | Worker Supervisor | 每个 UI 组件自行启动或重启 |

调度器协调资源，执行器推进循环，状态服务保存状态，三者不是三套相互套用的循环。模型调用的重试所有权仅属于网关；执行器不能收到异常后自行换一种调用重复请求。

## 2.3 建议目录，不要求机械搬迁

```text
src/shared/contracts/          命令、事件、错误、版本、运行时 schema
src/core/application/          项目、任务、审批、文档等用例服务
src/core/domain/               客户端语义、状态机、候选与提交规则
src/core/runtime/              执行接口、模型网关、工具网关、上下文
src/core/runtime/adapters/     legacy、pi，第三方类型到此为止
src/core/scheduling/           长任务与资源协调
src/core/infrastructure/       repositories、objects、outbox、diagnostics
src/core/compatibility/        项目兼容、旧状态读取、迁移注册
src/ui/data/                   查询缓存、分页、事件归并
src/ui/features/               按现有页面与功能逐步拆分
```

`electron/main.ts`、`preload.ts`、`worker.ts` 保留入口语义。`service.ts` 逐步缩为组装与路由，不把大量逻辑一次移动到另一个同样巨大的文件。相互依赖用显式小接口处理；不新增没有第二种用途的抽象层。

增加静态依赖检查：UI 不得引用 core infrastructure；domain 不得引用 Electron 或代理 SDK；adapters 不得引用正式提交仓储；只有组合入口允许同时认识具体实现。

# 3. 统一命令、错误、事件与 IPC

## 3.1 单一契约来源

沿用并核对当前 Zod 主版本，在同一声明中绑定 command 的参数 schema、结果 schema、错误码、访问类别、幂等规则和超时类别。由声明导出 TS 类型与命令白名单；不手写另一套前后端类型。

公共调用的目标形态是 `invoke(command, params, options)`，返回类型由 command 自动推断，不能由调用方指定一个任意 `invoke<MyType>` 伪造结果。边界输入先当作 `unknown`，校验通过后才得到类型；不使用不受控 `any` 穿越进程边界。

迁移期间可提供旧调用 shim，但它必须调用同一契约，记录使用位置，并在最终阶段移除。对参数扩展是接受、忽略还是拒绝须按命令明示；涉及提交、路径、权限的对象默认严格校验。

## 3.2 请求信封与能力绑定

以下字段是拟定语义，具体编码由真实仓库实现：

```text
Request: protocolVersion, requestId, operationId?, command,
         workerGeneration, projectSessionId?, projectId?, params
Response: requestId, ok, result | error
Event: protocolVersion, workerGeneration, projectSessionId?, projectId?,
       uiSequence, type, resourceId?, resourceVersion?, payload
```

`requestId` 标识一次运输请求；`operationId` 标识一个业务意图，写操作用它去重。两者不能合并。`projectSessionId` 在每次打开、重新打开或切换项目时生成，即便项目 ID 相同，也拒绝旧会话命令污染新会话。

主进程保持来源窗口／frame 校验、命令白名单和用户选择路径的能力绑定。路径不能仅凭 renderer 自报就放行。来源检查不能被“已经有 Zod”替代。[S1:L100-L112；R5]

## 3.3 超时、取消与结果不确定

查询是有期限的短请求；启动长任务只在任务记录可靠写入后返回 `runId` 与初始状态，不能把整轮生成挂在一个 IPC Promise 上。正式采纳、备份等可能跨多个步骤的操作返回可查询的 `operationId`。

使用可配置超时类别；P00 依据现有延迟设置默认值，并用假时钟测试。IPC 超时表示调用方没有等到结果，不表示后端动作未执行。写操作超时后先查询 `operationId`，不能产生一个新意图盲目再执行。

`AbortSignal` 不通过 IPC 直接传输；通过明确取消命令、请求／任务 ID 及本地控制器映射实现。区分“取消等待响应”“请求任务取消”“当前任务确实停下”。取消正式提交时，若已跨数据库提交点，只停止后续用户任务，不撤销既成提交，继续安全收尾。

所有 pending 请求在成功、失败、超时、取消、worker 退出和窗口销毁时释放计时器和监听。迟到响应不重新兑现 Promise，但业务状态可由正常查询恢复。写操作收到迟到成功不能被记录成未执行。

## 3.4 错误分类

至少覆盖：`VALIDATION_ERROR`、`PROTOCOL_MISMATCH`、`PROJECT_SESSION_STALE`、`PROJECT_VERSION_UNSUPPORTED`、`VERSION_CONFLICT`、`APPROVAL_STALE`、`PERMISSION_DENIED`、`BUDGET_UNCONFIRMED`、`BUDGET_EXCEEDED`、`REMOTE_RESULT_UNKNOWN`、`WORKER_UNAVAILABLE`、`TIMEOUT_WAITING_RESPONSE`、`STORAGE_FAILURE`、`CANCEL_REQUESTED`。

错误包含用户可读消息、traceId、可执行恢复动作枚举和经脱敏的细节，不把底层堆栈、请求头或密钥直接传给 UI。不要只使用一个含义模糊的 `retryable: true`；恢复动作要区别查询、恢复本地同步、重试无副作用读取、申请新的付费尝试。

## 3.5 实时事件不是持久化事务日志

保留 worker 代次、项目标识、去重和缺口纠偏。UI 事件序号可以在新代次重置；任务持久日志序号必须由数据库单独管理，二者不能混用。[S1:L139-L166]

资源事件携带变更资源与版本，界面只失效对应查询。文本增量可批量显示；资源状态和正式内容以持久化后的查询结果为准。UI 通知失败不回滚已经成功的数据库提交，界面通过缺口检测重拉恢复。

# 4. 统一执行对象与状态机

## 4.1 对象语义

| 对象 | 定义 | 关键关联 |
|---|---|---|
| Session | 持续交互上下文，映射已有 conversation 等实体 | 项目、消息、多个 Run |
| Run | 一次有目标、来源版本与预算的执行 | executor 版本、父任务、上下文依据 |
| Step | 一个逻辑执行步骤，可含模型尝试或工具阶段 | Run、序号、输入与结果引用 |
| Attempt | 一次实际远端请求尝试 | 调用目的、发送状态、结果确定性、费用 |
| ToolCall | 一次有作用域的工具执行意图 | Attempt、调用 ID、工具版本、参数哈希 |
| Candidate | 一个不可变的待审阅修改提案版本 | 内容哈希、依据版本、依赖、来源 Run |
| Approval | 可信客户端对具体候选和范围的批准记录 | 指纹、权限范围、有效期策略 |
| Commit | 一次正式状态变更 | 候选、审批、事务、目标修订、物化状态 |

这是客户端自有语义，不把第三方同名 `turn` 直接映射成数据库同名字段。旧会话表先复用，不强制新增重复 Session 表。

## 4.2 Run 状态与转换

建议 Run 状态：`queued`、`running`、`waiting_input`、`waiting_permission`、`paused`、`blocked_unknown`、`succeeded`、`failed`、`cancelled`。原业务状态通过兼容映射继续展示，不能直接丢弃“需要修改”“过期”等含义；它们可能转移到候选或业务任务投影。

| 当前状态 | 可接受动作 | 下一状态／条件 |
|---|---|---|
| queued | dispatch / cancel | running / cancelled |
| running | ask_input / ask_permission / pause | waiting_input / waiting_permission / paused |
| running | possible_remote_ambiguity | blocked_unknown |
| running | finish / fail / cancel_settled | succeeded / failed / cancelled；取消已实际收尾 |
| waiting_input | submit_input / cancel | queued / cancelled；校验任务类型接受的输入 |
| waiting_permission | approve_action / deny_action | queued / paused 或 cancelled；按该动作策略 |
| paused | resume / cancel | queued / cancelled；先检查恢复资格 |
| blocked_unknown | reconcile_known_result | 根据可靠结果恢复到 paused、succeeded 或 failed |
| blocked_unknown | authorize_new_attempt | queued；记录明确授权，新建 Attempt，不覆盖旧 Attempt |
| blocked_unknown | abandon | cancelled；旧请求的结果／费用不确定性仍保留 |
| terminal | read / create_successor | 不直接重写为 running；新执行建立有来源关系的 Run |

“收到取消请求”保存为控制意图 `cancelRequestedAt`，不得立即伪装为执行已停止。即使 Run 被放弃，Attempt 的远端费用状态也可能仍未知。对 waiting 状态收到过期或重复回复，必须有幂等与版本检查。

Run 的 `succeeded` 仅代表执行达到目标，不代表候选已采纳或文件已同步。执行器完成、用户审阅、正式提交必须在界面分开表达。

## 4.3 候选、审批和提交状态

候选内容一旦进入 `pending_review` 就不可原地修改；修改产生新版本并使旧审批失效。候选审阅状态可采用 `pending_review / approved / rejected / superseded / stale`。编辑中的独立草稿继续由 Draft 管理，不混为已批准候选。

Commit 可采用 `prepared / db_committed / materializing / completed / conflict / failed_before_commit`。`db_committed` 之后不能变为“从未提交”。`conflict` 要保留已提交修订、未同步文件、外部文件副本和用户可执行操作。界面“已采纳”由 Commit 关系派生，不建立另一套可能不同步的真值。

## 4.4 统一转换器

所有新状态修改经过一个具名转换函数或等价服务：读取当前版本 → 验证动作合法 → 校验前置条件 → 同一事务写状态和关键事件 → 提交后通知 UI。使用 `stateVersion` 或等价比较交换规则拒绝并发旧写入。

禁止随处 `run.status = ...`。迁移期间旧 runner 必须通过适配层请求状态转换。为每条合法与非法转换建立数据驱动测试，覆盖取消、项目切换、重复消息和状态已推进的竞争情形。

## 4.5 恢复位置

保存明确的 `resumePoint` 与依据：尚未开始、发送意图已记录、远端结果未知、工具结果已持久化、等待输入、候选已生成、等待审阅、数据库已提交待物化。

默认恢复只进行本地状态重建与安全收尾；自动启动新的模型、搜索或 embeddings 请求全部禁止。用户明确恢复需要新调用时，重新校验价格、预算、模型配置、权限和来源；配置或依据改变不沿用旧审批，必要时创建后继 Run。

# 5. 持久化边界、事件与数据权威

## 5.1 数据权威表

| 数据 | 权威来源 | 可重建／派生部分 |
|---|---|---|
| 正式文档所指向的内容版本 | 数据库修订关系 + 校验通过的内容对象 | 普通展示文件、UI 缓存 |
| 尚未纳入客户端的外部修改 | 磁盘实际内容及保存的冲突副本 | 待比较记录；不能把它当作垃圾覆盖 |
| Run 状态、Attempt、工具结果 | 项目数据库中的执行记录 | 运行中内存、UI 时间线 |
| 会话原始消息与 provider 续轮数据 | 选定的一套客户端持久记录 | 框架内存、规范化展示消息 |
| 候选与审批 | 候选不可变版本及可信审批记录 | 差异视图、状态徽标 |
| 全文／向量索引 | 正式来源版本与索引配置 | 索引本身可丢弃并重建 |
| 压缩摘要／模型推测 | 带来源标识的派生对象 | 不能反向升级为正式设定 |
| 用户未提交编辑 | 现有编辑缓存／独立草稿 | 不能被后台正式状态刷新覆盖 |
| 密钥 | 主进程安全存储中的凭据 | 运行时最小必要解密值 |

结构化记录存在文档解析入库与数据库生成文件两种方向，必须逐类型建立 owner 表，不能统一假定一律数据库为主。[S1:L264-L264] 先盘点并保留行为，再消除具体的双向不确定性。

## 5.2 最小增量数据模型

先检查现有 `runs`、`events`、`conversation_turns`、`action_proposals`、`draft_artifacts`、`changesets`、`applied_transactions`、`materialization_outbox`，优先扩展或封装。[S1:L210-L225]

需要承载的逻辑记录如下，表名不作强制要求：

| 逻辑记录 | 最低字段 |
|---|---|
| execution run | runId、executorId/version、state/stateVersion、resumePoint、baseSnapshot、manifestRef、parentRunId、createdAt |
| model attempt | attemptId、runId、stepId、purpose、provider/configVersion、dispatchState、resultState、usageState、pricingVersion、requestRef、responseRef |
| tool execution | scopedCallId、runId、attemptId、toolName/version、argsHash、effectClass、status、resultRef |
| approval | approvalId、candidateId/version、fingerprint、scope、actorKind、issuedAt、revokedAt、consumedByCommit |
| operation receipt | projectId、operationKind、operationId、inputHash、status、resultRef |
| budget reservation | reservationId、runId、attemptId、amount/currency、certainty、status |
| checkpoint | runId、sequence、resumePoint、stateRef、executorStateVersion |

列表不是要求新建七张表。若现有 JSON 内容已经可靠承载某项数据，优先加 schema 校验、索引和唯一约束。凡新增持久格式都要有显式版本和读写兼容策略，不把第三方类实例直接 JSON 序列化当永久格式。

对存在重复风险的数据设置数据库唯一约束，而不是只在代码中“先查再插”。例如同项目同操作类型同 `operationId` 唯一；工具的去重键带 Run／Attempt／调用编号的作用域；同一正式提交意图只有一个事务结果。

## 5.3 关键事件与显示增量分离

关键事件包括：执行获准、发送意图、工具即将产生副作用、工具结果、用户决定、候选产生、正式提交点。关键状态与对应事件尽可能写入同一 SQLite 事务，并等待成功之后再执行下一个外部动作。

显示用 token delta 可以批量传输和批量持久化，不要求每个字符同步刷盘。发生崩溃时尚未持久化的增量必须标明是局部恢复，不可伪造完整回答；已可靠记录的工具结果和提交点不得丢失。

提供类似 `appendCriticalAndCheckpoint()` 的可等待接口。不能把 `eventEmitter.emit()` 或 `for await (event)` 当成“数据库写入已经完成”的保证。Pi 文档区分等待订阅者的 Agent 接口和仅观察的低层事件流；接入版本必须实测这一点。[R2] DeepSeek 的显式 flush 边界可作为参考，但不是要求照搬存储格式。[R4]

UI 通知走非关键的提交后分发通道，不参与关键数据库事务的提交条件。持久化失败立即停止后续模型／工具动作；不能吞掉错误后继续消耗费用。

## 5.4 远端请求前后落盘顺序

```text
校验状态、上下文、模型配置与预算
→ 事务内建立 Attempt、预算预留、发送意图和恢复点
→ 等待事务可靠完成
→ 发送远端请求
→ 接收与解析响应，保存必要增量
→ 保存完成结果／不确定状态及费用状态
→ 结算或保留预算预留
→ 才允许执行模型返回的已完整校验工具，或推进下一步
```

“发送意图已落盘，但是否实际发出不清楚”的崩溃窗口，必须保守标记为可能发送，不能重启后直接当作未发送。只有能够证明还没有进入发送路径的记录，才可以按未发出处理。

模型响应是否完整、用量是否明确、远端是否执行完成是不同维度，不压缩成一个成功／失败布尔值。费用信息缺失不能写零。

## 5.5 工具副作用与去重

只读工具可以在明确策略下重读；草稿写入必须通过事务幂等写入实现；不可幂等的外部副作用本轮不开放。相同参数哈希不代表相同意图，不能把两次不同任务的同内容写入全局去重。

同一个已完成 ToolCall 重放时返回持久结果，不再执行 handler。同一调用键出现不同参数哈希视为协议冲突。已开始但结果未落盘的工具，按照 effectClass 和专门的恢复函数判断；没有证明不能自动重做。

# 6. 正式提交、审批与文件同步

## 6.1 保留链路，只收紧入口

第一轮不重写现有 `storage.ts` 提交算法。先用回归和故障注入锁住行为，再把它包为明确的 `ProjectCommitService`。其职责仍包括候选指纹、依据检查、对象保存、事务准备、数据库提交、outbox 和同步恢复。[S1:L238-L262]

所有原有的保存／恢复历史／结构化变更入口必须盘点：业务上属于正式状态改变的，最终统一走受控提交入口；本来就属于显式用户直接编辑保存的，保留它的确认交互，不强行改造成多次 AI 候选审批。不得改变已有手动保存语义。

## 6.2 候选指纹与审批

候选指纹至少覆盖：候选规范化格式版本、项目标识、基础修订／快照、拟变更目标及内容哈希、依赖来源版本、操作范围，以及会影响允许操作的规则版本。采用稳定规范化编码再求哈希，测试字段顺序、空值、Unicode 和换行差异；不能使用易变展示字符串作为指纹。

是否把已有规则与配置字段加入指纹，应依据实际业务影响判断并记录；不能把无关 UI 时间戳加入，造成无意义失效。审批记录单独保存签发时间、撤销、有效期策略和消费关系。

审批由可信的客户端应用服务生成，记录为本机用户动作，不接受模型生成的批准字段。审批凭据不得放入模型消息、工具参数或普通日志。该机制约束正常客户端流程，不宣称能抵御已经控制本机进程的攻击者，也不伪称能证明物理真人点击。

再次采纳时必须在提交保护区内复核候选、审批、项目与依赖版本。旧审批对新候选一律无效。版本冲突的解决方式是保留差异、重建候选并重新确认，不提供隐藏的“忽略所有检查”开关。

## 6.3 本地幂等与数据库提交点

同一采纳意图采用稳定 `operationId`；唯一约束、批准消费和正式状态推进必须在同一数据库事务内协调。重复请求返回已有 Commit 及物化进度，而非创建另一个正式修订。

同一候选版本还必须具有唯一的正式 Commit 归属。即使两个窗口分别生成了不同 operationId，也不能把同一候选采纳两次。使用候选版本唯一约束或等价原子消费规则，不能仅依赖客户端复用 operationId。需要再次应用相同文字时，必须根据当前依据创建新的候选；部分采纳的范围也必须固定到新的候选指纹中。

正式提交之前允许失败并保持旧正式状态；数据库提交之后只能继续物化、报告冲突或通过新的正式变更进行修正。不能把已提交事务标成未发生，不能通过删除 outbox 隐藏失败。

本地数据库可以建立受测试约束的幂等提交语义，但不能由此承诺远端模型 API exactly-once 或绝不重复计费。

## 6.4 外部文件竞争与平台限制

继续使用内容对象、临时文件、刷盘、替换和事务恢复记录。同步前比对预期磁盘版本；发生冲突保存外部内容和待物化版本，向 UI 暴露明确差异与处理入口。

不能声称“写入前 hash 检查 + rename”消除了所有外部写入竞争。外部程序可能在检查与替换之间继续修改。P03/P04 中必须在真实 Windows 文件系统上验证替换／保留旧文件策略；覆盖窗口中的被替换内容必须有可恢复的保留机制或拒绝继续写入。无法证明不会丢失内容时，进入冲突而不是盲目覆盖。

并非要求在本轮自行编写复杂 native 文件系统库；优先复用已验证的平台能力和现有安全实现。新增原生依赖必须有必要性和打包测试。对不受客户端锁约束的外部程序，不作不可能的全局串行承诺。

应覆盖文件被占用、重命名失败、权限拒绝、磁盘空间不足、临时文件残留、路径大小写／保留名、符号链接或 reparse point、项目目录被移动。每一类失败都保留可解释状态。

## 6.5 正式数据完整性检查

提供只读诊断：数据库引用的对象是否存在且哈希匹配，outbox 是否有对应事务，正式修订是否指向有效内容，候选依赖是否可读。检查失败时先阻止相关写入并提出安全恢复路径，不自动删除疑似损坏记录。

# 7. 模型网关、费用与重试

## 7.1 唯一调用入口

所有文本生成、规划、上下文压缩、评估、摘要，以及本次执行链中的搜索和 embeddings 费用，必须关联主任务。文字模型统一经过 `ModelGateway`；非文字外部服务可以保留专门 adapter，但共用调用登记、取消、权限和费用账本。

模型列表查询等管理请求也登记用途与凭据来源，但不强行把它们伪装成生成 Run。是否计费按实际服务与配置处理。现有主进程与业务进程分散的网络出口逐步收敛，不顺手删除已有代理配置和连接测试。[S1:L342-L366]

## 7.2 Provider 契约

保留四类原协议的消息、工具、结束原因、流式与续轮差异。规范化输出用于上层理解，原始 provider 续轮数据作为有版本的私有附件保存，隔离在 adapter 边界。

不得把 Anthropic 内容块、Gemini 特定片段或 Responses 续轮字段强行压成普通文本后宣称无损。按实际支持内容建立 fixtures；无法无损映射的协议组合必须停用该新执行器路径，继续由旧适配路径提供功能。

所有请求记录模型 ID、provider 类型、配置版本和价格版本。中途更改服务地址或凭据时，不允许旧请求自动切换到新地址继续，也不沿用错误的认证头。

## 7.3 费用账本

金额使用明确精度的整数最小计价单位或 Decimal，记录币种和比例，避免直接累加二进制浮点。没有汇率依据时不跨币种混算。用户配置的价格保留版本，不能用今天的价格改写历史账单。

预算校验至少包括：

```text
已确认费用 + 未结算在途预留 + 结果未知的潜在费用
+ 本次拟请求的保守预留 <= 可用预算
```

以上三类记录必须互斥结算，不能把同一个未知请求同时算进两份预留。费用预留与执行许可在统一事务或等价原子区中完成，避免并发重复占用余额。父 Run、辅助 Run 和评估使用同一父预算约束，不能各自得到完整额度。

无法估算可靠上界时，不称为“严格预算已保证”。预算模式开启时默认阻止此类自动调用，说明缺少价格／用量／最大输出等哪一项。用户显式允许超出原预算时要生成新的预算决定，不静默放宽限制。

输入输出 token、缓存读写、推理用量等按 provider 实际返回和定价规则处理；未支持字段保留原始用量并标记计价不完整。接口实际计费可能与本地估算不同，不向用户承诺绝对金额上限。

## 7.4 重试与取消分类

| 情况 | 默认策略 |
|---|---|
| 参数／本地容量校验失败，尚未进入发送意图 | 修复输入后可以创建新的受控尝试，不产生远端重复问题 |
| 只读本地工具暂时失败 | 按有限次数策略重读，记录次数 |
| 请求可能发送，断线／超时／本地取消 | 标记结果未知，不自动重新发起 |
| 返回明确错误响应 | 按该 provider 已验证语义分类；HTTP 状态码本身不证明未计费 |
| 用户明确选择重新请求 | 记录风险确认与新 Attempt，重新预留费用 |
| 数据库已提交、文件同步失败 | 仅恢复本地物化，不请求模型 |

自动网络重试初始设为零；只有对已验证无副作用／不会重复付费的具体调用才能启用有限重试。必须检查并关闭 SDK、HTTP 客户端和执行器内部隐藏重试；无法控制则该执行器不通过正式接入门槛。

`abort()` 表示本地停止等待或发送取消信号，不代表远端一定停止执行或计费。用户界面区分取消请求已发送、执行已停止和远端结果未知。

## 7.5 协议边界测试

必须覆盖 SSE 分片跨字节、跨 JSON、工具参数分多段、重复结束消息、截断工具参数、异常 finish reason、空回复、超大响应、用量缺失、到达超时后迟到完成、代理与重定向、工具 ID 冲突、原生续轮字段保真。完整解析与 schema 校验之前禁止执行工具。

# 8. 受控工具、规则资源与安全边界

## 8.1 工具注册契约

每个工具声明：名称与版本、输入／输出 schema、effectClass、授权范围、超时、取消策略、是否允许并行、输出上限、恢复／幂等策略和日志脱敏方式。先校验参数，再检查权限、Run 状态、预算与来源版本，再登记执行意图，最后执行。

初始 effectClass 只开放 `read`、`draft_write` 和 `candidate_proposal`。正式提交不在模型工具清单中。工具错误用结构化错误返回，不伪装成成功文本，且不能因错误文本包含指令而放宽下一步权限。

## 8.2 领域能力替代通用文件权限

建议提供版本化读取、带范围的检索、草稿版本创建、候选提议、待审阅查询与受控评估能力。名字跟随现有产品；不要新造写作业务流程。

通用 `terminal` 和任意 `network` 继续禁用，这与原说明一致。[S1:L308-L310] 搜索走现有受控接口；不得因接入编码代理而自动安装 shell 工具、读 HOME、读取浏览器配置或修改 `.novelclient`。

工作区是可选兼容手段：从固定快照导出允许资料到隔离临时目录，记录 manifest；代理只生成草稿输出；校验目标路径、编码、大小和来源后导入候选。隔离目录不是安全沙箱，必须另外限制进程能力；未完成隔离时不运行不可信代码。

## 8.3 路径、网络与密钥

保留 sandbox、contextIsolation、禁用 nodeIntegration、CSP、DOMPurify、导航限制和来源验证，不能为打包或调试关闭。[S1:L368-L388；R5]

文件访问用项目／文档 ID 和受控相对路径解析，拒绝目录穿越、绝对路径逃逸、符号链接／reparse point 绕过、大小写混淆及控制目录访问。校验路径不能仅做字符串前缀比较。

受控网络访问沿用当前允许服务地址与凭据绑定，限制重定向、超时、响应大小。网页提取应拦截不允许的内网／环回／元数据地址并处理重定向后的地址检查；对用户明确配置的本地模型地址单独授权，不与任意网页抓取共用豁免。

实际安全能力受现有库与平台约束，测试记录具体覆盖范围。不能只写“已 sandbox”就当作网络、文件和凭据访问全部隔离。

密钥只在可信主进程／业务进程调用需要时存在，不注入模型可见工具环境，不进入 SDK 自动遥测、crash dump 上传或导出报告。服务地址变化继续要求重新确认相应凭据。

## 8.4 提示注入与来源可信度

用户提供的规则与系统策略、检索正文、外部网页、工具返回和模型推测分区标记。资料里的“忽略之前指令”“读取密钥”等文本只作为资料，不取得工具权限或用户审批资格。

不能依靠提示词防御代替代码校验。被注入的模型即使请求不允许操作，Tool Gateway 也必须拒绝。规则资源版本和哈希随 Run 固定；运行中更新规则不能悄悄改变已批准范围。

## 8.5 插件／MCP 边界

本轮只允许可信内置工具。MCP、子代理、任意插件市场和模型生成代码执行为未启用扩展，不作为本轮完成条件。即使后续接入，也必须通过本工具网关和费用账本，不获得正式提交权。

不可信插件不能与数据库连接、正式项目目录和凭据共处一个无隔离运行环境。新开子进程本身不等于降低操作系统权限；Pi 和 DeepSeek 的公开实现不能替代本产品的安全边界验证。[R2；R3]

# 9. 上下文、检索和派生记忆

## 9.1 保留已有检索，重构组装方式

保留 SQLite FTS、精确字符串补查、结构化过滤、现有 embeddings 及来源哈希／索引代次，不引入独立向量服务。[S1:L344-L355] Context Builder 只接受版本化来源引用，输出明确的输入清单，而不是返回一段无法追溯的大字符串。

清单至少含：来源 ID／版本／hash、读取范围、类型、必要性、可信度、权限、选用理由、token 或字节估算方式、是否截断、检索配置和构建版本。必要资料无法容纳时停止发送，不能为了让请求成功而偷偷删掉它。

## 9.2 三层上下文

固定约束层放任务目标、用户要求、权限和输出规则；工作集层放本轮必需正文与资料；可检索层放资料索引和按需读取入口。原业务提示词内容保持不变，只改变供给与追踪方式，任何提示词策略变化单独评测。

对已有业务数据，明确正式已采纳内容、未采纳草稿、讨论设想、外部资料和模型推断。来源没有明确提供的写作领域结构不能凭本方案新造；P00 按实际字段建立分类映射。

## 9.3 压缩策略

压缩是可选的派生步骤，默认先裁剪可选旧结果和重复内容，再考虑付费摘要。压缩调用通过 Model Gateway，关联 Run 与费用。压缩对象保留来源覆盖范围、生成模型与规则版本、遗漏项和失效条件。

不能把摘要作为唯一事实或删除原始来源；不能让摘要覆盖正式设定；不得压缩掉未解决冲突、用户否定、权限限制、待批准事项和恢复锚点。使用“固定决策／未决问题／当前依据／已完成步骤”结构组织摘要只是建议，不替换现有业务语义。

新资料使摘要过期时标记失效；恢复任务前重新验证。引入上下文压缩不等于已经解决长期任务可靠性，仍需检查点和阶段交接。[R6]

## 9.4 容量检查

按真实 provider 能力使用 tokenizer 或计数接口。没有可靠计数时保留带安全余量的估算并明确标记，不把 UTF-8 字节数改名为 token。为输出、系统与工具定义、下一步工具结果预留容量；压缩器自身也要能放入它的请求窗口。

模型配置变更后重新计算容量。不得把任意第三方兼容端点都假定为官方同名模型的上下文大小。附带多模态输入时按实际支持检查；不支持则明确拒绝，不静默丢弃。

## 9.5 检索和索引失效

索引作业固定来源 hash、索引配置版本和 projectSession。计算可在后台进行；提交索引前再次比较来源版本，不一致就丢弃过期结果或重新排队。检索返回可解释来源，不能把旧向量与新文本组合成错误引用。

正式提交更新和索引失效应有可靠关联；不要为了简化把每次提交都同步重建全库索引。

# 10. 调度、项目生命周期与 worker 监管

## 10.1 资源调度，而非一把全局 busy 锁

先实现单项目调度器，不扩大为多项目并行产品。作业分为交互任务、评估、索引、导入、备份、文件同步、迁移和清理，声明资源、优先级、取消方式、恢复点及费用属性。

| 操作 | 默认并发规则 |
|---|---|
| 读取固定快照 | 可并行，固定来源并 pin 必要对象 |
| 多个独立草稿生成 | 第一版默认串行；预算／取消隔离验证后才开放有限并行 |
| 同一文档草稿修改 | 串行或版本冲突检测，不能后写覆盖前写 |
| 正式数据库提交 | 单项目串行、短事务 |
| 同一路径文件物化 | 串行、按目标版本检查 |
| 索引与评估计算 | 可低优先级执行，发布结果前校验来源 |
| 备份 | 建立一致备份屏障；与迁移／清理互斥 |
| 迁移、项目关闭、破坏性清理 | 维护状态排他；不在活跃写入中实施 |

锁定顺序必须统一，避免嵌套互相等待。不能持有数据库写事务去等待模型网络响应或用户审批。等待输入、权限和审阅时不占用活跃模型执行槽，但保留持久任务与必要对象引用。

对持续后台任务设置公平性，避免长期饿死，也不能拖慢用户采纳和取消。资源声明违反或重复调度必须产生可诊断错误。

## 10.2 取消与阶段停靠

取消从 UI 命令到调度器、执行器、HTTP、工具和后台作业贯穿。长循环在检查点响应；不支持中断的同步 SQLite 操作只能在事务边界停靠，不能假装 AbortSignal 已经中断它。

较大文件／索引作业分批执行，批次间释放事件循环。确需 worker thread 时只迁移计算任务或专门连接所有权，不把同一个 DatabaseSync 连接跨线程随意共享。任何新增执行单元仍受统一调度和诊断管理。

## 10.3 项目切换

停止接收旧项目新任务 → 将可暂停任务停在安全检查点 → 安全收尾已提交事务 → 等待持久化与句柄释放 → 关闭旧项目数据库与锁 → 创建新 projectSession → 打开新项目。

不能通过固定 sleep 假设旧项目已经关闭。旧 worker 回调与后台结果带项目会话标识，发现过期立即丢弃，不写入新项目。用户未提交编辑必须保留或明确提示，不能因切换而被快照清空。

## 10.4 worker 状态与握手

建议 supervisor 状态：`stopped / starting / ready / draining / exited / degraded`。启动握手验证协议版本、应用构建版本、worker 代次和能力，完成配置初始化与项目安全恢复后才对外 ready。

IPC 断连或心跳失联不等于进程已退出。重启前必须确认旧 worker 已结束或完成受控终止，不能并存两个拥有相同项目写入权限的业务进程。

异常退出时：拒绝旧 pending 请求并标记结果可能未知；记录退出原因；有限重启；重新初始化可信配置；重新获取项目锁与检查数据库；只恢复本地记录和 outbox，不恢复新的付费推理；向 UI 发布新代次与恢复摘要。

重启具有指数退避、抖动和熔断，默认建议最多连续尝试 3 次，具体间隔作为配置并用假时钟测。持续失败进入 degraded，允许导出脱敏诊断或安全关闭，不无限重启。该数字是方案默认值，不是现有行为。

## 10.5 正常退出

```text
main 发出 shutdown 请求
→ worker 进入 draining，拒绝新任务
→ 发出取消／停靠指令
→ 收尾关键记录与已提交事务
→ flush 必要日志，关闭数据库与项目资源
→ 确认释放项目锁
→ worker 回复 shutdown-complete
→ main 结束进程与窗口
```

设置有上限的退出等待和可见状态，不能无限等待；到达上限时说明未收尾对象，保存可恢复记录后按平台策略退出。强制结束不能让用户误以为所有远端请求已经取消。修复原说明中的短定时退出问题，不增加一层更长固定 sleep 代替握手。[S1:L408-L408]

## 10.6 项目锁

现有 PID 锁保留兼容读取，再增加实例 nonce、启动标识和拥有者信息；根据平台能力验证进程身份，减少 PID 重用误判。心跳过期只能作为异常信号，不足以直接偷锁。无法证明旧拥有者结束时拒绝自动写入，给出恢复说明。

本轮默认支持本地 Windows 文件系统；网络共享、云盘同步目录等未验证环境必须明确限制或警告，不能把本地锁保证外推到多机协作。

# 11. 执行器接口与 Pi 接入验证

## 11.1 接入顺序

先让现有 runner 实现客户端自有 `ExecutorAdapter`，跑通真实产品路径。随后只验证 Pi 的 agent core 组件级方案，不整体搬入其 CLI、TUI、默认 shell、插件系统或额外持久化系统。

选择 Pi 作为第一个实验对象的依据是官方核心提供可注入的模型流函数、上下文处理和工具执行接口。[R2] 这不是已证明它与本项目四类协议、构建环境或审批恢复语义兼容。必须固定实际验证的版本、锁文件、许可证和依赖摘要，不能直接依赖浮动主分支。

Codex App Server 的类型化协议和 thread／turn／item 分层可参考，但本轮不实现第二个完整服务式适配器。[R1] DeepSeek 的持久化和模块边界可参考；其安全说明要求独立进行风险判断，不能直接把默认高权限运行配置接入真实项目。[R3；R4]

## 11.2 接口要求

不要把这里的示意当成某第三方 SDK 的可复制 API。实际 TS 接口必须结合既有类型实现并通过编译。最小能力为：

```text
ExecutorAdapter.describe()               返回 ID、版本、支持的能力与限制
ExecutorAdapter.execute(context)         推进当前已授权 Run
ExecutorAdapter.restore(checkpoint)      仅重建本地执行状态，不自动联网
ExecutorAdapter.requestControl(action)   在允许检查点接受暂停／输入／取消
ExecutorAdapter.dispose()                释放监听与运行资源

ExecutionContext:
  run 的不可变依据和版本
  ModelPort：唯一受控模型请求入口
  ToolPort：唯一受控工具入口
  ContextPort：版本化上下文构建
  CheckpointPort：可等待的关键持久化
  ControlPort：取消和持久控制意图
  EventSink：非关键显示事件
```

第三方工具的 `execute` 只能委托 Tool Gateway。第三方请求流必须转到 Model Gateway，并保留取消与原协议数据。上下文转换必须可解释，不重复拼接系统指令、工具定义或已经提交的消息。

`restore()` 不等于 `resume()`：前者绝不触发新请求；后者必须经过客户端恢复决定、预算与权限校验才调用 execute。任何 SDK 的 `continue()`、follow-up 或自动后续推理都必须在网关再次取得授权。

不把第三方原生内存作为唯一可恢复状态。客户端保留原始消息、工具结果、规范化视图及必要的框架私有 checkpoint 附件；这些分别注明权威与派生关系。

## 11.3 准入清单

| 门槛 | 验证方法 | 不通过的处理 |
|---|---|---|
| GATE-01 所有模型子调用受控 | 用 spy／假 provider 统计网络与网关入口 | 不启用该路径 |
| GATE-02 无隐藏重试与自动恢复请求 | 超时、断流、进程恢复故障注入 | 不允许正式接入 |
| GATE-03 四类协议按支持矩阵保真 | 使用原协议录制／合成 fixtures 续轮 | 不支持的组合继续 legacy |
| GATE-04 关键持久化确实等待 | 阻塞 checkpoint，观察是否提前执行工具 | 不能靠异步观察日志补救 |
| GATE-05 工具权限不可绕过 | 伪造工具、路径、批准字段 | 必须拒绝并记录 |
| GATE-06 取消与项目切换可靠 | 中断模型／工具阶段，切换会话 | 不污染其他任务与项目 |
| GATE-07 预算可计入辅助步骤 | 压缩、follow-up、多工具后续调用 | 不漏账，不超授权 |

| GATE-10 许可证与供应链可交付 | 锁版本、保存许可与依赖清单 | 缺项不能发布 |

所有组合不必一次全部切换。按任务类型 × provider × 能力版本建立显式支持矩阵；不支持项创建任务前直接选择 legacy，并显示实际执行器。禁止在一个 Run 请求结果未知后偷偷改用另一个执行器重做。

## 11.4 实验流程与失败分支

第一步只读资料分析；第二步在独立草稿上生成；第三步输出符合客户端 schema 的候选；第四步通过现有用户审阅与正式提交链。每一步先用可重复的假 provider，再在用户授权费用与数据范围后做小规模真实模型烟测。

对比新旧执行器时固定任务、输入快照、规则与模型配置；同一真实任务不默认影子双跑，不把“对比实验”变成双倍付费。离线回放用于确定性测试，真实生成质量另做人工比较。

Pi 不通过门槛时，交付完整的准入失败报告、最小复现、受影响能力和 legacy 保留路径。不能通过删除检查或接入无关大框架完成验收。此时“统一 Harness 架构”阶段可以验收，但“新执行器接入”必须标记未通过，不能写成全部完成。

只有新的 ADR 明确批准另一方案时，才验证 OpenCode 或 DeepSeek 的完整服务式适配器；不在本轮自动展开多框架集成工程。

## 11.5 已存在任务和版本绑定

每个新 Run 保存 executorId、executorVersion、checkpointVersion、工具与规则版本。任务进行期间锁定执行器，升级只影响新任务；已开始旧任务由对应兼容恢复路径处理。

不能让未知版本 checkpoint 默认套用最新解析器。无法恢复的记录保持只读可查看，提供从既有结果／候选建立后继任务的显式操作，不删除历史。第一版不实现跨不同框架迁移活动执行栈。

# 12. UI 数据刷新、状态展示与编辑保护

## 12.1 先分状态所有权，再决定库

保留当前 React 与编辑器，先分离：临时 UI 状态、未提交编辑状态、持久业务资源、运行中显示增量。可以建立小型查询缓存或复用仓库已有库；不为本轮必须安装新状态框架。

`app.snapshot` 保留作为启动、纠偏与兼容接口，逐步拆出项目摘要、文档元数据、当前正文版本、Run 列表／详情、候选、会话分页、索引和 outbox 状态等资源。正文与长日志按需获取，不在每次状态变化重复携带。

禁止把任务事件更新直接覆盖编辑器本地未保存内容。编辑状态要记录所属项目、文档与基础版本；检测正式版本变化时提示比较／合并，不无声清空草稿。`localStorage` 的旧缓存保持兼容读取，在明确成功迁移之前不能删除。[S1:L114-L128；L196-L196]

## 12.2 分页与事件处理

历史采用稳定排序字段加 ID 的游标分页，明确 limit 上限和下一页游标；不能在并发追加消息时因 offset 漂移重复或漏掉记录。旧整段读取接口逐步退役，但用户仍能访问完整历史，不把以前上限以内之外的数据删除。

按资源 ID 去重与批量失效。文本流独立节流，后台评估事件不应让全部会话重载。乱序旧 resourceVersion 不覆盖新版本。发现事件缺口、worker 代次变化、项目会话变化时重新获取相关快照并重设基线。

## 12.3 必须可见的运行信息

保留现有页面布局，增加或校准状态：排队、执行中、待输入、待权限、已请求取消、已停止、远端结果未知、候选待审阅、审批过期、正式状态已提交但文件待同步、外部冲突、worker 恢复中。

用户操作由服务端返回的合法动作和任务能力决定；例如不支持补充指令的恢复任务，UI 不展示或发送该参数。服务端仍做校验，不能只依赖按钮禁用。

费用区分已确认、预估、在途和未知。错误提示提供一次明确动作，避免把所有问题都称为“重新生成”。文件同步冲突不能出现会重新请求模型的默认按钮。

# 13. 数据兼容、备份、清理与回退

## 13.1 分开管理版本

应用构建版本、IPC 协议版本、数据库 schema、项目结构、正式修订、快照、内容哈希、模型配置、规则、索引代次和执行器 checkpoint 版本必须分开。[S1:L410-L426]

统一 `ProjectCompatibilityService` 或等价实现：打开、导入、备份读取、恢复、回收站和清理共用结构识别与能力判断。不能只在一个 `if (version === 1)` 后面加 `|| version === 2` 就宣布全部兼容。

原说明版本值仅是历史基线，P00 读取真实值。迁移编号按实际 schema 序列递增，不能照本文件猜下一版本。新程序面对未知未来版本时不写入；无法确认只读安全时连只读也应明确拒绝。

## 13.2 增量迁移流程

迁移前建立隔离备份并验证可读取。进入项目维护状态，确认没有并发写入和 outbox 危险窗口；按照现有恢复依赖先完成必要恢复或暂停迁移并报告，不能在不一致状态上盲目改 schema。

优先添加兼容字段／新表／索引，不直接删除旧历史字段。建立迁移注册表：源版本、目标版本、前置检查、备份要求、执行脚本、校验、失败处理和最小可读写应用版本。小型 schema 更新可在事务内完成，大量文件或分批数据更新必须有持久进度和重入保护。

迁移过程不得改写正文内容哈希来“清洗”历史，不得把旧未知值改成已知成功。旧字段确实无法推断的新状态标为 legacy／unknown 并限制危险操作，不臆造缺失审批或计费信息。

完成后检查外键、唯一约束、对象引用、关键记录数量、内容哈希、候选关联、事务与 outbox 一致性。迁移重复执行要识别已完成并无副作用。

## 13.3 兼容矩阵

测试至少覆盖：当前仓库支持的每个旧项目结构版本、每个仍支持的数据库版本、空项目、有历史项目、有待审阅候选、有结果未知请求、有待物化事务、有外部冲突、损坏配置和未知未来版本。

每个样本注明允许读取、允许写入、是否自动迁移、需要怎样备份、迁移失败如何恢复。不要由“schema 添加了列”推断旧应用一定能安全写新数据。

## 13.4 一致备份与恢复

沿用 SQLite 备份接口，不复制运行中的主数据库文件来代替一致备份。[S1:L404-L404；R7] 项目完整备份还包含对象、普通文件、事务记录和必要元数据，不能只备份 SQLite。

在明确的备份屏障固定数据库与对象引用，阻止并发清理；复制时校验 hash 与 manifest。外部普通文件变化要被检查并标明快照边界，必要时有限重试或报告不一致，不能声称多个独立文件天然原子快照。

恢复到新目录并验证，不覆盖原项目；恢复后的写锁不得继承旧活跃 PID；先检查版本与完整性，再允许打开。测试备份中断、缺对象、校验失败、磁盘满与目标目录已有数据。

## 13.5 历史保留与垃圾回收

首个交付只实现容量统计和 dry-run，不默认删除正文、历史、未采纳候选或未知请求记录。清理策略在用户显式启用后生效，不因新版本启动就执行旧数据大清洗。

可清理对象必须经过可达性分析：正式修订与快照、候选、草稿、运行检查点、会话附件、事务／outbox、审批关联、备份 pin 和正在使用的检索来源都是根。把“当前正文没有引用”误判成垃圾是禁止的。

清理分为标记、隔离、保留期、最终删除，能中断恢复；先校验再删引用孤儿，不按文件年龄直接删除 objects。清理与备份／迁移互斥，计算时 pin 活跃引用。删除日志先处理脱敏与保留规则，不影响恢复证据。

## 13.6 三种回退必须分开

功能回退：关闭新执行器对新任务的选择，保持统一内核与数据格式。代码回退：撤回某批源码，但先确认它仍能处理现有数据。数据回退：使用已验证备份恢复到新目录，并明确备份后新增数据的保留／导出方案。

禁止把“安装旧版”描述为无条件安全。需要维护最小读写版本；未知新版数据拒绝旧版写入。不能通过删除版本标记强行让旧程序打开。

升级失败不删除用户目录，不更改 appId 和默认 userData 路径，不生成第二套看似丢失旧数据的配置位置。实际安装标识以 P00 读取结果为准。

# 14. 诊断、性能与发布

## 14.1 统一诊断链

贯穿 traceId、requestId、operationId、projectSessionId、runId、attemptId、toolCallId、candidateId 和 transactionId。一次用户采纳能够追踪到审批、正式修订、outbox 和文件同步；一次未知请求能够找到发送意图与费用不确定原因。

日志结构化并限长，禁止默认记录密钥、认证头、完整正文或 provider 私有敏感数据。用户主动导出的诊断默认脱敏；需要内容样本时单独选择，显示范围并保留不包含正文的选项。

应用版本来自统一构建元数据并对照实际安装产物，修复写死版本。新增指标包括：IPC pending 数量、超时、事件缺口、队列等待、模型尝试数、预算预留、未知请求数、工具耗时、同步重试、worker 重启、数据库／文件 I/O 耗时和事件循环延迟。

不能把评估器执行与 telemetry 记录混为一个组件。评估作业归调度器，诊断只负责记录与展示，不应记录一条日志就自动发起付费评估。

## 14.2 性能基准与阈值

P00 记录机器、OS、磁盘、Node／Electron 版本、构建模式、夹具规模、预热和重复次数。使用纯合成或用户明确授权脱敏的样本，不使用真实作品做压力破坏测试。

建议规模：S 为 100 文档／总正文约 1 MB／1,000 事件；M 为 1,000 文档／约 10 MB／10,000 事件；L 为 5,000 文档／约 50 MB／100,000 事件。按机器资源调整并保存真实参数，这些是测试负载建议，不是产品容量承诺。

测量项目打开、文档切换、Run 列表、长会话分页、搜索、采纳、备份、外部扫描、流式期间 UI 更新、取消与 worker 恢复的 p50/p95；记录进程内存、数据库大小和事件负载。模型服务耗时与本地框架耗时分开。

建议门槛：同条件本地关键交互 p95 不较基线恶化超过 10%；出现超过 10% 的可重复退化必须解释并修复或有明确批准，不能忽略。稳定资源事件不应触发无关整库／全会话读取。高频文本更新不能增长无界队列。阈值不是现有性能事实，应在 P00/P09 固定基准后使用。

## 14.3 文件检测优化

在保留正确性的前提下，优先用文件事件 + 去重／合并 + 低频全量校验替代固定两秒全目录扫描。文件 watcher 只是变化提示，不是权威事实；启动、丢事件、目录重命名和异常恢复都需要重新核对。

自有写入事件去重不能忽略同期外部写入。读取外部变化要处理未写完的临时状态；用稳定性检查和版本对比，不因连续事件马上导入半截文件。忽略 `.novelclient` 内部缓存的规则不能漏掉真正恢复记录或用户正文。

仅当实测显示需要时，把重计算或大量文件处理放到专门 worker；不要在没有证据时替换 SQLite 或引入网络服务。

## 14.4 Windows 发布验收

沿用现有 Vite／esbuild／electron-builder／NSIS 交付链，实际脚本以仓库为准。[S1:L441-L454] 验证 dev 和打包版行为一致，ASAR 内外资源可定位，内置资源清单与 hash 一致，依赖的 ESM／native 模块可在目标 Electron 中加载。

至少覆盖全新安装、覆盖升级、卸载保留策略、旧项目打开、无网络启动、模型配置损坏恢复、非 ASCII 与空格路径、权限受限目录和单实例限制。必须在 Windows 目标环境验证关键文件竞争与安装行为；其他平台 CI 不能代替此项。

签名／自动更新若仓库尚未完成，本轮提供接口边界、需求和发布检查清单，不把没有证书或账号的事情伪造为已完成，也不自动购买、注册或发布。修复现有发布可靠性不以新增自动更新系统为前提。

# 16. 测试架构与故障注入

## 16.1 测试分层

继续使用仓库已有测试框架与脚本，新增单元、契约、集成、故障恢复、UI 和打包烟测。不要为了重构顺手更换测试框架。必要时添加内部测试辅助层，但不能让测试专用绕过权限的入口暴露在生产构建。

单元层测试纯状态转换、schema、指纹、费用计算、版本能力和恢复决策。契约层验证 typed client、preload、main、worker 的参数与错误一致。集成层使用真实临时 SQLite 与对象目录验证事务、候选、审批、outbox 和旧项目迁移。故障层在独立进程中硬终止并重新打开同一夹具，不以抛异常代替所有崩溃测试。

UI 测试验证合法按钮、编辑缓存、分页、事件纠偏、费用未知和同步冲突显示。打包测试运行目标 Windows 产物，验证依赖、资源和文件操作。外部真实模型烟测必须与本地测试分离，有明确授权、费用上限和脱敏输入。

## 16.2 建议故障注入点

```text
FI-01 发送意图落盘之前
FI-02 发送意图落盘之后、网络请求调用之前
FI-03 请求发出、响应未开始
FI-04 模型文本已部分到达、完成结果未落盘
FI-05 模型完整结果已落盘、工具执行之前
FI-06 工具意图已落盘、handler 调用之前
FI-07 草稿事务完成、工具结果通知之前
FI-08 候选保存后、UI 收到通知之前
FI-09 审批保存后、正式提交开始之前
FI-10 对象已保存、正式数据库提交之前
FI-11 正式数据库提交成功、outbox 执行之前
FI-12 文件替换完成、物化完成记录之前
FI-13 文件版本检查后、实际替换之前插入外部写入
FI-14 迁移分批完成一半
FI-15 备份数据库完成、对象复制未完成
FI-16 worker draining 过程中主进程异常退出
```

每个注入点记录初始状态、已跨越的可靠写入边界、预期恢复动作、不得发生的动作和最终校验。网络副作用使用可计数的假服务记录接收次数，确保恢复后没有隐藏重发。文件内容用 hash 和实际 bytes 双重验证。

FI-02 的正确默认是“可能发出，阻止自动重发”，即使该测试注入位置实际尚未调用网络；除非实现额外存在能在崩溃后证明未发出的机制。保守不确定性是设计的一部分。

## 16.3 自动化环境保护

测试工具启动时校验所有可写路径位于本次临时根目录内，显式隔离 Electron userData、项目与备份位置。向真实用户目录、仓库外项目路径、真实服务端发送请求均默认失败。

提供无网络假 provider，能模拟流式分片、用量缺失、工具返回、多轮、断开、超时和迟到响应。测试真实取消不能依赖睡眠碰运气，使用可控屏障、假时钟和握手。

断言不仅检查状态标签，还检查请求次数、工具副作用次数、正式修订次数、对象引用、审批绑定、outbox 和保留的外部内容。这样才可识别“界面显示成功但实际重复执行”。

| T-031 | 同工具调用键出现不同参数 | 拒绝协议冲突，而非复用错误结果或重新执行 |

| T-033 | 路径穿越、链接与控制目录访问 | 拒绝越界，真实目标无变化 |

| T-036 | 候选产生后内容被修改 | 原候选不可变或产生新版本，旧审批不可用 |
| T-037 | 审批后依赖、项目或范围变化 | 拒绝旧审批，不自动放宽版本检查 |
| T-038 | 同一候选重复点击采纳，包括不同 operationId | 候选版本只有一次正式归属／修订／事务 |

| T-043 | 同步期间外部文件变化 | 保留外部内容、产生冲突，不静默覆盖 |
| T-044 | 检查和替换之间插入外部写入 | 被竞争内容不不可恢复丢失；平台实现证据齐全 |

| T-046 | 代理事件订阅持久化被阻塞 | 关键持久化完成前不得执行下一副作用 |

| T-048 | 必需上下文超容量 | 不发送；提示缺少容量而非偷偷裁剪必需依据 |
| T-049 | 摘要过期／模型设想与正式事实混合 | 保留来源类别，过期摘要不覆盖正式资料 |
| T-050 | 旧索引／评估完成时来源已改变 | 丢弃或标记过期，不污染新版本 |

| T-056 | 迁移中断并再次打开 | 按进度恢复或安全回到未迁移状态，无半兼容写入 |
| T-057 | 未知未来项目／数据库版本 | 拒绝不安全写入，错误说明真实版本 |
| T-058 | 备份恢复及 WAL 中有数据 | 恢复包含已提交数据与全部必要对象 |
| T-059 | 备份缺对象／hash 错／复制中断 | 校验失败，原项目未被覆盖，目标不可假装可用 |

# 18. 分阶段实施任务书

## 总顺序与阶段门禁

```text
P00 只读盘点与基线
 → P01 已知缺陷与命令契约
 → P02 IPC、项目会话与进程生命周期
 → P03 统一执行状态、持久化与兼容数据模型
 → P04 候选审批与正式提交内核封装
 → P05 模型／工具网关与预算
 → P06 上下文、任务调度与恢复整合
 → P07 单一新执行器接入验证
 → P08 UI 资源化与恢复交互
 → P09 性能和后台作业优化
 → P10 历史治理、完整兼容和发布回退
 → P11 全量验收与交付
```

每阶段内部可以拆成多个小提交。只有相关测试通过、前置能力就绪后才启用新路径。不要把所有内容做到一个大提交后才跑测试。架构迁移的临时双路径要有用途、到期条件和状态，不能永久形成两套权威实现。

### P00：仓库盘点、保护与基线

**目标：** 确认真实事实与可复现环境，不修改业务行为。

P00-1 检查仓库、适用指令、未提交变更、包管理器、锁文件、应用标识与目录配置；建立隔离测试配置，确认不会打开真实数据。

P00-2 阅读关键模块和全部模型、工具、存储出口，建立 `repository-audit.md`、`feature-inventory.md`、`call-path-map.md`；逐项比对 BASE-01—09，注明真实代码证据。

P00-3 读取已有脚本，记录真实类型检查、单测、集成、打包和运行命令；运行环境能支持的基线验证。未运行、失败与通过分别记录，不能引用旧 143 项结果。

P00-4 构造旧项目、待审阅、未知请求、outbox 冲突等合成夹具；记录数据库与对象 hash；确认备份与恢复入口可在隔离目录工作。

P00-5 完成初始性能测量、威胁边界和数据权威映射；生成 `TASK_STATUS.md`，把所有阶段初始化为待处理，P00 用真实证据更新。

**产物：** `docs/refactor/` 下的审计、命令清单、功能清单、兼容样本清单、基线报告、风险登记。可先只添加文档和测试基础，不大规模重排目录。

**验收：** 能独立复现测试环境；真实数据未被触碰；所有未知项已写明。实际缺少仓库时只报告阻塞，不能假装开始改代码。

**回退：** 删除新增隔离夹具与工具不影响产品；不自动删除用户已有文件。

### P01：修复具体不一致，建立命令契约

**依赖：** P00。

P01-1 对 BASE-01—03 先写可失败的隔离回归，再实施最小修复；若真实仓库已修复，新增覆盖并记录，不重复改实现。

P01-2 统一项目结构能力判断，覆盖打开、导入、备份读取、恢复、回收站和到期清理；保持原支持范围，拒绝未知版本。

P01-3 建立 command → input/output/error 的单一 schema 声明，先迁移项目打开、任务启动／恢复／取消、候选审阅／采纳、诊断导出等高风险链路。

P01-4 补 typed client 与 preload 白名单导出；所有旧调用通过受控 shim，建迁移列表，随后逐步迁移其他命令。

**产物：** 兼容服务、契约注册、类型测试、已知缺陷回归、实际版本来源。不能先全局重命名所有 API 再修运行失败。

**验收：** T-001—006 及相关旧业务回归通过；非法输入编译和运行时均被识别。所有新接口不出现跨层 `any`。

**回退：** 保留兼容 shim；已修缺陷不因关闭新契约路径而回归。不得回退为重复版本判断。

### P02：IPC 生命周期、项目会话与 supervisor

**依赖：** P01。

P02-1 引入 requestId／operationId 区分、短请求超时、pending 清理、可查询长操作；写意图去重先复用现有持久记录，必要时做最小增量 receipt 迁移，P03 再统一模型，不能只内存去重或等待后续阶段才保证幂等。

P02-2 引入 workerGeneration 和 projectSession，所有跨进程命令与事件有过期校验；事件订阅生命周期完整。

P02-3 实现启动握手、退出握手、draining 状态和可解释超时；配置损坏时保留原文件并提供兜底读取，避免静默覆盖。

P02-4 实现有限重启和熔断；先仅恢复进程与展示连接，自动项目恢复必须等 P03／P06 的本地恢复测试通过后启用。任何版本都禁止自动推理。

**产物：** supervisor、IPC 请求注册表、会话隔离、配置恢复辅助与集成测试。

**验收：** T-005—018、T-062 的本阶段路径通过；无 pending 泄漏；用真实子进程验证退出与代次。

**回退：** 可临时关闭自动重启，保留安全关闭与请求清理；不能重新依赖 300／500 ms 定时退出。

### P03：执行对象、状态机与可靠持久化

**依赖：** P01、P02；实际迁移必须先有隔离备份证据。

P03-1 盘点旧 Run 状态与业务含义，完成 `legacy-state-mapping.md`，建立 Run／Candidate／Commit 分离后的投影与兼容读取。

P03-2 实现统一转换器、stateVersion 与控制意图；旧 runner 通过适配请求状态变化，不再新增分散赋值。

P03-3 增量承载 Attempt、ToolCall、审批、operation receipt、budget reservation 与 checkpoint；优先复用现有表。建立迁移版本、唯一约束和重复执行测试。

P03-4 建立关键日志＋状态同事务写入与可等待检查点，区分显示增量；记录发送意图与不确定性窗口。

P03-5 实现只读恢复分析器：输入持久状态，输出安全可用动作，不调用网络、不执行正式写入。后续本地恢复动作单独通过权限入口执行。

**产物：** 自有执行类型、状态机、repositories、兼容迁移、checkpoint、恢复决策表。

**验收：** T-008—012、T-019—022、T-046—047、T-055—057；迁移前后正式内容 hash 不变，事件／状态不半提交。

**回退：** 优先回退新写入路径而非删除字段；读取新数据前校验最小版本。不能未经兼容证明安装旧版读写已迁移项目。

### P04：封装审批和正式提交内核

**依赖：** P03。

P04-1 列出全部正式写入入口，建立 Commit Kernel 接口并调用原已验证算法；保留手动编辑保存的现有交互。

P04-2 明确不可变候选版本、指纹字段与审批作用域，加入审批撤销／消费与重复采纳唯一约束。

P04-3 将 outbox 作为独立可调度本地恢复操作；数据库提交点之后的错误和取消不伪装成未提交。

P04-4 加固外部变更冲突与文件替换保护；在 Windows 隔离目录测试检查—替换竞争和文件占用，记录平台保证边界。

P04-5 补只读完整性检查和 FI-08—13 崩溃测试；UI 暂时可通过旧 snapshot 展示新状态，不等待 UI 大改。

**产物：** Approval Service、Commit Kernel 外观、可靠物化恢复、完整性诊断、故障测试。

**验收：** T-032、T-036—045 全部相关路径通过；同意图只一次正式提交；无需模型即可恢复本地同步。

**回退：** 保留现有底层事务实现和新安全校验；不得去掉审批绑定、事务日志和 outbox。

### P05：统一模型与工具网关、预算和重试

**依赖：** P03、P04。

P05-1 提取四类 Provider Adapter 并建立原协议 fixtures；在不改变行为的前提下让现有调用经过 Model Gateway。

P05-2 所有生成、辅助评估、压缩、搜索与 embeddings 调用登记目的、父任务、取消和费用；清点出网出口，消除绕过路径。

P05-3 实现原子预算预留、确定／预估／未知费用与单一结算；修复重复计入和预算并发竞争。

P05-4 明确发送意图与 Attempt 完成点，禁用隐藏重试；“结果未知后重做”必须有独立授权和新 Attempt。

P05-5 实现 Tool Gateway 的 schema、权限、effectClass、受作用域去重、结果持久化、输出限制和工具错误；正式提交始终不作为模型工具。

**产物：** Model Gateway、Tool Gateway、预算账本、协议夹具、安全与取消测试。

**验收：** T-019—035、T-046；所有远端调用都能归属和限制，截断工具调用不会执行，真实密钥不会进入日志。

**回退：** 允许 provider 内部继续复用旧实现，不能绕过网关恢复隐藏自动重试。

### P06：上下文、统一调度和恢复整合

**依赖：** P03—P05。

P06-1 提取 Context Builder 与 manifest，保留原 FTS、向量、规则与必要／可选选择；补容量检查与来源分类。

P06-2 实现资源调度、统一取消、后台评估／索引作业，保证等待审阅不占活跃执行槽；不默认提高并发数。

P06-3 为索引与评估增加提交前版本检查，防止过期结果写入。按需增加批处理，避免持有数据库事务等待网络。

P06-4 将本地恢复与 supervisor 连接：先锁与完整性，再事务与 outbox，再恢复可读 Run／候选；所有新付费动作等待明确授权。

P06-5 可选增加派生摘要，若无法保持来源／预算／恢复语义则保持关闭，不能因“缺上下文压缩”绕过容量保护。

**产物：** 上下文 manifest、调度与取消、统一恢复摘要、后台作业版本屏障。

**验收：** T-013—018、T-024—025、T-048—050；核心恢复不联网；索引过期结果不会影响正式来源。

**回退：** 关闭新摘要与优化并行，保留原检索算法和新版本校验；不丢 manifest 与恢复记录。

### P07：可替换执行接口与 Pi 实验

**依赖：** P03—P06 的安全门槛通过。

P07-1 把现有正式 runner／conversation runner 包为 Legacy Adapter；共享循环机制但保持两类业务策略，不强行合并全部业务逻辑。

P07-2 验证当前官方 Pi agent core 的来源、版本、许可、Node／Electron 兼容和调用接口，锁定单一版本，形成 ADR 与能力矩阵。

P07-3 实现 Pi Adapter 对 Model／Tool／Checkpoint 的桥接；不开放默认 shell、任意网络、自动插件、第二份会话真值和自主审批。

P07-4 顺序验证只读、独立草稿、候选、既有审批提交链；按 GATE-01—10 做 conformance 测试，并保存不支持组合。

P07-5 默认用 mock；授权后才做真实烟测与质量对比。提供新任务执行器开关和 Run 固定版本，不支持中途偷偷 fallback。

**产物：** ExecutorAdapter、Legacy Adapter、候选 Pi Adapter、能力与协议支持矩阵、准入报告、ADR。

**验收：** T-026、T-028—032、T-046、T-063—066；全部硬门槛通过才允许对应组合启用。必须如实区分“实验可用”“正式准入”“不支持”。

**回退：** 对新任务切 legacy；旧实验任务保留记录和只读结果，不能删除后重跑假装无影响。未通过不宣称新执行器交付完成。

### P08：UI 查询、分页、状态与编辑保护

**依赖：** P01—P06；Pi 未准入不阻塞 UI 基础改造。

P08-1 按资源拆查询与订阅，保留 `app.snapshot` 纠偏；迁移高频刷新路径，不要求同时换状态管理库。

P08-2 长对话、任务与历史改为稳定游标分页，保留完整可访问历史；按资源版本去重与失效。

P08-3 显示 Run、审阅与 Commit 分离状态，正确呈现未知费用、取消中、同步冲突和 worker 恢复。

P08-4 将编辑缓存与正式资源分离，测试后台刷新／项目切换不清空未保存编辑；支持的用户动作来自能力声明并服务端再校验。

**产物：** 查询层、分页契约、拆分后的页面状态、恢复与冲突 UI、前端回归测试。

**验收：** T-002、T-039、T-051—054、T-070；不相关事件不全量重拉，编辑与旧功能完整。

**回退：** 可以按资源切回 snapshot 读取，不能恢复清空编辑或错误恢复参数的行为。

### P09：性能、后台作业与文件检测

**依赖：** P06、P08，并有 P00 基线。

P09-1 在相同环境和夹具下重测，识别实际瓶颈，先优化重复查询／无意义刷新和长同步任务。

P09-2 将全目录频繁扫描改为事件提示、合并队列和低频校验；验证丢事件、目录移动与自身写入竞争。

P09-3 索引、备份和导入按检查点分批并受调度控制；确有收益才引入 worker thread 或专用执行单元。

P09-4 记录 p50/p95、内存、event-loop delay 与消息大小，修复未解释退化；新增计量本身不得成为大量同步 I/O 来源。

**产物：** 可复现实测脚本、基线对比报告、已证明收益的优化、回归说明。

**验收：** T-050、T-054、T-069 与原故障测试继续通过。性能改善不能通过减少完整性检查或关闭日志恢复获得。

**回退：** 每项优化有独立关闭或撤回路径；文件 watcher 不可靠时回到低频校验，不能停止外部变更检测。

### P10：历史容量、完整迁移与发布回退

**依赖：** P03、P04、P08、P09。

P10-1 扩展旧项目与未知版本兼容矩阵，验证空项目、长历史、未完成事务、未知请求和损坏配置。

**产物：** 兼容矩阵、备份恢复报告、dry-run 报告、发布检查清单、功能／代码／数据回退说明。

**验收：** T-055—064、T-067—068；未知版本不写入，恢复验证通过，升级不改变用户数据位置。

**回退：** 使用前述三类回退策略；不删除项目新数据，不把旧安装包当数据修复工具。

### P11：全量验收与最终交付

**依赖：** 所有拟发布能力的前置阶段完成。

不能因为外部 SDK 的设计不同就删除客户端正确性约束。无法通过边界接入的 SDK 保持实验状态，而不是成为修改审批、预算或数据权威的理由。
