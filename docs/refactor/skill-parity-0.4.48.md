# 0.4.48：传输稳定性、格式兼容和可复用上下文

本轮处理三类实际问题：Sub2 出口长连接不稳定；完整提交及合法局部修改被误判；阶段切换时重复输入相同规则和资料。0.4.45—0.4.47 的三份诊断样本完整保留，最终验证使用新项目独立计时。

## 实现

- Sub2 专用入口首选已经连接探针验证的 VLESS 出口，保留健康检查和后备线路。源站证书校验开启；TLS 恢复仅限能够证明尚未发送 HTTP 请求的握手失败。生成已经开始后的中断不自动重发整轮。
- 完整文档的冗余 `final:true` 按完整提交处理；规划阶段允许在当前已授权文件范围内做精确 patch。来源哈希、唯一锚点、版本、路径权限、模板及完整性检查保留。
- 网络恢复保留成对的工具调用、校验反馈和已保存草稿，不清空历史后重新生成。
- 接受相邻规划阶段后，保存真实请求前缀，并追加当前任务及变化资料。作者设定、同路径同哈希完整资料和已完整生成的相同版本文档不重复输入。
- 公共规则按名称和完整内容哈希分块，只复用同名同版本全文。新阶段保留明确的规则引用；变化规则发送完整新版。专项任务、模板及工具权限仍由当前阶段提供。用户资料不会因去重被提升为指令。
- 正常采纳导致的宿主进度更新允许追加；外部改写、权限变化、受限视角、正文及独立审查使用当前完整资料。上下文过大时重建，不删当前必要内容来维持缓存率。
- S05—S08 从首次请求起使用稳定的串行工具设置。首事件、最后有效事件和断流信息进入诊断，帮助区分握手与已发送后的中断。

参考 [DeepSeek Harness runtime-context](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/core/agent-loop/src/runtime-context.ts) 的追加式上下文及变更检测架构。本客户端独立实现持久化、来源版本和阶段权限约束，没有引入该运行时依赖。

## 验证和限制

真实 0.4.47 七次请求离线回放，未调用模型：原始资料和工具权限不变，当前公共规则全文各保留一次；S04 请求体相对旧样本减少约 5.3 万字符。结果见 `output/harness-validation-20261023/shared-rule-real-replay.json`。完整测试、打包校验及最终实跑记录另存 `output/harness-shared-cache-20261023`，以完成后的回执为准。

模型、推理强度、12 轮上限、30 章批次、原 Skill 模板、正文长度及独立审查要求保持不变。缓存命中以服务端 token 计量为准；相同前缀不等于服务端一定命中。Codex 原基线与客户端使用不同模型和推理强度，耗时比不是纯客户端开销；创作遵循同一设定及结构，也不能保证逐字相同。
