## 三、模型究竟要写哪些内容

每案不是一段简短灵感，当前数据合同要求：

| 字段 | 作者看到的内容 |
|---|---|
| title | 方案名称，仅标识方向，不是正式书名 |
| logline | 主角身份、目标、困境 |
| storyEngine | 反常机制、行动、代价、反制、下一轮难题 |

界面默认展示名称、故事梗概、展开机制和区别；开篇、首卷、长期风险等放在折叠区。折叠只减少屏幕占用，没有减少模型生成量。

## 六、为什么出现修订：本次有实际问题

首次审查发现推荐方向的“生存配额”口径不一致：梗概按地址发放资格，开篇出现单人通行证，又声称连接空楼就能救整栋楼，但没有说清空楼本来有什么资格、地址容量与人数的关系。

这个问题直接关系到第一场破局是否成立，是合理的因果检查；不宜为了提速把它统一降为不处理的建议。

修订后明确了地址资格、固定人口容量、接入条件，以及个人通行证不等于整栋楼资格。实际只修改第一案的五个文字字段。第二、第三案及公共元数据没有改变，却仍被完整生成和回传。

修订输出 JSON 共 4,478 字符，其中可直接复用的序列化内容约 3,327 字符，占约 74.3%。这是按字符估算重复内容比例，不是 token 节省或耗时节省承诺。代码确实规定修订时提交完整结构，已有内容没有由宿主直接合并。

另一个“身份能否拆分”的问题被评为 minor，最终仍保留为建议，没有阻止方向选择。因此不能把本次慢解释成“所有建议都被误报成错误”。

## 七、缓存与上下文交接的实际缺口

四次请求都带了相同的稳定缓存键，缓存并非完全没生效；第三、四次的 provider cachedInput 也证明了部分复用。

但这个专用通道没有完整使用此前的上下文交接优化：

1. `cache-session.ts` 的普通阶段 eligible 明确排除 `run.planning`，S10 分支也排除它。
2. `prompt-cache.ts` 按普通阶段的专项技能分隔符及 authorPremise/sources/contextPolicy 封套拆分。三案使用另一种拼接格式和 input/context 字段，不满足该条件。
3. 实际保存的请求因此都是“一个整体 developer 块 + 一个 user JSON”。生成和审查角色、工具及规则变化，无法像稳定公共块那样充分复用。
4. 每次成功切换子步骤都会清空 messages，再从当前输入/报告组装。独立审查不应继承生成者的推理和自评，但可以共享未经生成污染的作者输入及公共规则；目前这两件事没有在三案路径中分开处理。

结论：前期针对普通阶段与正文流程的缓存改进，不能等同于三案流程已覆盖；当前样本总缓存率仅 39.24%。也不应通过人为追加预热请求或扩大重复输入来把百分比做高。首轮新输入、工具结构和实际模型服务缓存状态均需按真实结果评价。

## 八、为什么等待体感更差

请求已经启用流式传输，模型主要返回函数参数增量。provider 会累积这些参数，但三案执行器等整份工具结果完整返回、解析和本地校验后才设置 report。界面能在独立检查期间展示首版三案，选择按钮要等检查完成；它不能在第一个方向刚写完时就预览第一案。

## 九、供下一步逐项修改的优先级

1. 明确“三个方向”的内容深度：保留机制、主角选择、代价、第一场兑现和区别；把完整世界细则、长篇经营细案留给选定方向后。不用缩字数代替质量标准。
2. 给三案检查单独的规则包，保留必要的因果与可写性核查，避免默认带入 204 条通用正文规则。相同作者要求在输入中只保留一份清晰权威版本。
3. 把新增方向和局部修改分开提交：修改时只提交允许位置的新值，宿主与原报告合并并验证；最终保存给 UI 的三案结构保持不变。两案未变时不让模型复写。
4. 为三案流程接入稳定公共输入与独立审查分支；保留审核独立性，复用作者事实，避免把生成者的推理、自评和结论带给审查者。
5. 增加只读流式方向预览；完整检查之后再允许选择或采纳。无需增加模型请求。
6. 再评估是否让审查调用直接给出有边界的小修订，从四次缩减到两次；这是职责变化，需要单独验证，不能把“取消复查”直接当作内容质量不变。
7. 给界面分别展示首个内容时间、生成时间、检查时间和追加修订时间。把真实修订原因说清楚，不让一条“生成中”覆盖所有动作。

本次交付的是事实核查和修改依据，并未实施上述新方案。后续每阶段都应先确定输入、应输出的内容、允许自动处理的问题及结束条件，再改动代码和验证。
