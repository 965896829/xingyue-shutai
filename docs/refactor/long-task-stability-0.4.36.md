# 0.4.36：长篇规划分段保存与连接诊断

## 复现与原因

2026-10-22 对截图对应任务进行只读检查，确认故障发生在 S08 的三十章批量细纲生成。

- 第一次请求约 500 秒后失去 WebSocket 连接。Sub2API 在相同时间记录上游 `read frame header: EOF`；同批连接还出现 ping 超时。
- 作者手动恢复后，再次生成完整长文，达到客户端已经配置的 600 秒请求期限。两次失败都没有完整文件候选，已接受的前序阶段仍然存在。
- 原执行方式只有完整模型响应通过校验后才运行 `propose_changes`。长文件集中在一次响应中，故障会丢失本轮尚未完成的工具参数；单纯加大超时不能提供断点。
- WebSocket 断开码未包含在有限恢复的代码分类中，本次补齐。是否恢复仍取决于作者设置、已收到内容、总次数和费用边界。

日志可以确认上游连接断开，不能据此确定是代理节点还是远端服务主动关闭。因此本机线路调整作为有记录、可回滚的运行配置修复，并通过真实请求验证；不将一次成功解释为外部网络永久稳定。

## 客户端实现

保留现有十一阶段、模型适配器和候选采纳机制。S05—S08 增加可选的分段草稿协议，其他阶段仍使用原来的文件候选接口。

1. 长篇大纲、节奏和批量细纲按自然段组或一至五章生成，每段不超过 8,000 字符。
2. `propose_changes` 的 `append:true` 将新增内容保存为未完成草稿。首段 `draftHash:null`，后续必须引用前段回执中的精确哈希；`baseHash` 始终指向正式文件版本。
3. 每段在既有 SQLite 工具事务中保存，工具回执与运行记录一起提交。断流、退出、重启或上下文重建保留已完成段落。相同工具回执不会重复追加，旧草稿哈希不能再次写入。
4. 资料读取阶段仍可并行调用工具；有未完成草稿后顺序写入，避免多个追加同时依赖同一个哈希。
5. 最后一段 `final:true` 才合并为完整文件候选，运行原有规范化、字段检查和审阅。分段次数不消耗整份文件的语义修复次数。
6. 未完成草稿不能被采纳，也不能由“候选已经齐全”的本地恢复逻辑放行。草稿内容参与审阅指纹，已保存段落可在任务页展开查看。

原整份文件提案仍兼容，旧运行记录没有 `documentDrafts` 时按原逻辑读取。结构化字段为可选项，使用现有数据库备份，不新增作品目录迁移。现有作品未被测试工具写入或执行。

分段会增加请求次数和上下文传递开销，不承诺缩短总生成时间。既有轮数、工具次数和费用预算仍生效，不会为完成任务静默提高上限。

## 连接与恢复

Responses 请求增加客户端请求关联 ID。WebSocket 异常记录关闭码、最后事件类型、事件数、响应 ID 和距最后事件的时间，用于与 Sub2API 日志对齐；不记录鉴权头或私有推理内容。

有限恢复新增 `WEBSOCKET_CLOSED` 和 `WEBSOCKET_CONNECTION_ERROR` 分类。取消、永久拒绝、次数耗尽、部分可见回复、无法保证费用上限的情况仍会停止。结果未知的请求不会被当作免费、可安全无限重放的请求。

恢复读取本地草稿并发起后续请求，不能取回已经中断且未完整返回的那一段。对于 `store:false` 的 Responses 调用，使用保存的原生历史和当前上下文，不依赖已经关闭的连接缓存。参见 [OpenAI WebSocket 恢复说明](https://developers.openai.com/api/docs/guides/websocket-mode#reconnect-and-recover)。
