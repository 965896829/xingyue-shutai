# 命名治理与验收（原文拆分）

## 八、旧名称、别名与入口兼容

以下只用于客户端输入的兼容判断，不宣称这些名称已经被番茄官方合并、更名或下线；未经核验，不将它们自动视为同义分类。

| 输入名称或标签 | 规则选择方式 |
|---|---|
| 悬疑恋爱 | 采用实际世界背景＋悬疑规则＋关系称呼规则；不强行等同于女频悬疑。 |
| 奇幻仙侠 | 根据本书实际文化选择东方仙侠、西方奇幻或明确的混合规则；不直接二选一猜测。 |
| 现言甜宠 | 都市或现代社会命名＋关系称呼规则；校园和职场部分按实际场景补充。 |
| 纯爱 | 只据已确认的人物与关系处理；不能自动推定具体世界观、人物性别组合或叙事模式。 |
| 医术 | 作为专业领域叠加；按现代医学、历史医药或幻想医道分别处理，不互相替代。 |
| 综影视、综漫及具体作品衍生标签 | 加载对应原作版本与跨世界规则；保留来源，不把其他作品名称直接拼接成新实体。 |
| 无法识别的新分类或标签 | 使用通用规则与已确认世界设定，标记待建立映射；不冒充已完整适配。 |

## 九、反模板与连续性检查

### 9.1 必须拦截的新候选问题

出现下列问题时，修正或撤回新候选，不写入正式设定：违反作者明确禁用项；把反例当成候选；擅自增加设定以解释名字；与已确认事实矛盾；无依据改变实体身份、隶属关系或等级；泄露当前视角未知的身份；将未经核验的现实名称包装成已证实事实。

“问罪碑、验命石、审判钟”在新候选中属于明确禁用项。规则正文、审阅记录与既有稿件中的出现，不能因此触发盲目删除。

### 9.2 需要人工或上下文判断的问题

同音、形近、简称冲突、名称过长、生僻字多、称谓过于宏大、命名过于整齐、同一意象反复出现，以及“某某司、某某使”的批量生成，都进入语境审阅，而不是仅按字面一律判错。

不能把这些审阅项包装成可靠的“AI作者识别”结论。它们是可读性、风格和一致性检查，不证明文本来源。

### 9.3 检查项目

| 维度 | 核查问题 |
|---|---|
| 题材年代 | 是否符合当前时代、地域、文化与实际制度？ |
| 对象类别 | 读者能否在首次必要介绍后区分它是人物、地方、组织、职位还是物品？ |
| 职能层级 | 是否为“管理某事”自动起成某某司，或为“执行某事”自动起成某某使？职责与层级是否有依据？ |
| 阵营一致 | 同一组织的主体、分支、职位和建筑称谓是否自洽？例外是否已有明确依据？ |
| 读音字形 | 关键人物是否出现容易混淆的同音、形近或缩写？合理的家族共字是否被误判？ |
| 自然称呼 | 名字放进介绍、日常对话和紧张场景中是否都能自然使用？ |
| 模板密度 | 是否人人华丽、处处终极、全部同字数，或批量使用同一抽象词根？ |
| 信息边界 | 是否在名称、别名或称呼中提前泄露隐藏身份、规则和结局？ |
| 示例污染 | 是否把正向示例当作必选项，或把反例及其近义改写作为候选？ |
| 连续性 | 是否与已确认本名、旧称、身份、时间线或原作版本冲突？ |
| 核验范围 | 是否实际查过重名或事实来源？无法核验的内容是否仍保留不确定性？ |
| 修改权限 | 是否涉及已接受内容？是否已获得当前版本、当前范围的明确授权？ |

## 十、命名台账与客户端处理要求

### 10.1 每个正式实体应有稳定标识

实体标识不随改名变化。至少维护：对象类型、正式名称、常用简称、必要别名及类型、所属世界与时间线、所属地域与阵营、有效时期、知情范围、确认状态、规则版本，以及设定依据或首次有效出处。

复杂任务可以增加读音、关系性称呼、原作版本和避讳信息；并非每个路人或一次性普通物品都必须拥有完整档案。

名称相同不自动合并实体，名称不同也不自动拆成两个实体。转世、化名、同一物品的古称等需要作者已确认关系或明确文本证据，不能仅凭相似性推断。

### 10.2 输出模式

用户只要求正文时，直接使用通过检查、符合授权状态的名称，不把命名说明、评分和审阅过程插入正文。

用户要求起名时，按其指定数量提供；未指定时可默认给少量候选，每个候选只说明对象类型、简短依据和必要风险。不得要求用户从一大堆近义字排列中自行完成筛选。

用户要求审阅时，输出问题名称、所在上下文、触发规则、是否属于合理例外、建议处理方式与影响范围。未核验时不得声称“全网无重名”“符合所有历史资料”或“保证没有AI味”。

### 10.3 新名确认与改名流程

新名称先进入候选或草稿状态，在对应内容被作者接受后再进入正式台账。审校通过不等于作者确认，模型自评分高也不等于有权写入正史。

已接受名称需要调整时，先给出旧名、新名、改名原因、涉及实体、影响位置和不应修改的位置；作者确认当前版本与范围后再执行。已有明确且覆盖本次修改的授权，可以直接按授权执行，不重复索取同一确认；越出范围必须重新确认。

获准改名后，同步角色卡、人物关系、世界规则、各层大纲、细纲、当前有效正文、连续性台账及相关索引中的有效引用。同步应依据实体身份和语境，不做全书无差别字符串替换。

历史版本、审阅记录、原作引用、旧身份阶段的称呼、剧情中的假名及明确保留的旧称，不能随新名一并抹除。必要时登记为旧称或历史别名，让系统知道它们属于同一实体。

作者在确认后继续修改了相关稿件时，旧审批不能被用于覆盖新稿。更新失败时应保留可恢复版本、标明未同步范围，不能谎称全部一致。

### 10.4 权限落实

正式稿保护、版本校验、差异审阅、候选与正史分离，应由客户端的读取和写入流程落实，不能仅靠本规则中的文字约束。规则加载或关键上下文缺失时，不得静默跳过硬约束继续写入正式内容。

## 十一、最低验收用例

下列是检查规则是否正确执行的测试情境，不是故事设定。

| 测试情境 | 应有结果 |
|---|---|
| 无官署背景的仙侠宗门，模型批量把分支命名为某某司 | 指出制度套用问题，重新检查组织性质与命名方式；不擅自补建官僚体系。 |
| 已确认的历史官署或职称含司、使 | 按具体时代和制度核对，不因单字命中而判禁用。 |
| 已有阴间体系中出现阴司 | 作为条件例外处理，仍检查本书一致性。 |
| 现代公司出现数据中心或正常部门名 | 不因玄幻反例而拦截；检查是否符合现实或已确认架空语境。 |
| 新候选出现问罪碑、验命石、审判钟 | 拦截该候选；不得只换近义字继续套同一生硬模式。 |
| 用户已接受的旧正文包含上述反例 | 保留原文，提出审阅项；未经授权不改名。 |
| 作者只要求给一件物品起名 | 不因此添加测命、审判、天庭等新体系。 |
| 小说标为双男主或双女主 | 继承实际世界命名规则，不自动生成配套情侣名。 |
| 快穿进入新世界 | 采用该世界的命名空间，保留跨世界身份映射，不默认所有世界同名。 |
| 悬疑场景中只有化名公开 | 正文使用当前视角知道的称呼，不从后台台账泄露真实姓名。 |
| 获准只修改角色当前本名 | 更新授权范围内的有效引用，保留历史版本与剧情需要的旧身份称呼。 |
| 为了反模板而打乱已确认的军用编号或游戏等级 | 不通过；规则不能以去AI味为由破坏合理标准体系。 |

## 十二、最终执行原则

先理解世界，再判断对象；先沿用已确认语境，再创造必要的新名。

能朴素时不强装高深，需要庄重时不故意口语化；能准确说明功能时不强行隐晦，涉及秘密时不提前泄露。

同一文化要自洽，不同文化可以不同；历史感来自作品已经建立的生活、传承与变化，不来自批量古风词、混乱别名或整齐到失真的等级表。

对新候选先纠错，对已接受内容先守住授权边界。名字属于作品世界与人物生活，不是规则示例、分类标签或模型术语的复制品。
