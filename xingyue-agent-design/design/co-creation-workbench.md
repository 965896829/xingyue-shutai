# 对象驱动的持续共创

基线为星月书台 0.4.82，提交 b505f6f459db74871f39f63acf6106b827c8a353。本方案扩展现有对话、候选和修订系统，新增类型与提示词尚未接入运行时。

## 现有能力与新增边界

当前项目已经可以自由讨论人物、剧情、命名、改稿、题材和包装；任务对话可以绑定当前 run；候选可供读取，正式资料与自由草稿隔离。ActionProposal 保存项目版本、快照、模型、规则和来源，执行前检查是否过期。作者明确要求修改当前未采纳候选时，宿主能够依据 candidateEdit 直接执行修改，不需要再次点击确认。这些能力应继续保留。

本轮新增的是统一的对象入口、字段级讨论锚点、可独立采纳的差异、可比较的创作分支，以及同一对象在卡片、图谱、时间线和文档间的一致呈现。不要把现有讨论能力描述为缺失，也不要新建一个绕过原项目权限和持久化机制的聊天执行器。

| 能力 | 当前依据 | 本轮变化 |
| --- | --- | --- |
| 自由讨论与候选读取 | conversation-runner.ts 62–119、408–449 | 绑定具体对象、字段和版本，按需提供相关对象 |
| 任务内直接修改 | service.ts 1432–1479；conversation-runner.ts 205–219 | 复用明确授权路径，扩展为经宿主验证的对象范围 |
| 版本与过期检查 | conversation-runner.ts 224–240 | 增加对象 read set、依赖检查和合并判定 |
| 聊天持久化与分页 | conversations.ts 21–79 | 追加对象绑定和决策引用，不复制事实库 |
| 自由草稿与版本 | conversations.ts 104–155 | 草稿可关联对象与分支，继续隔离正式资料 |
| 执行与幂等回执 | service.ts 1507–1578 | 将通过验证的选择映射到现有 run、changeset 和 operation |
| 正式提交 | storage.ts 614–719 | 继续使用 SQLite、对象存储、提交日志与物化层 |

## 用户工作方式

作者从任何资料或图形对象进入“与AI讨论”，例如点击角色卡中的行为底线、章纲卡中的转折、世界规则中的代价。讨论顶部显示对象名称和当前版本；正文由当前对象及相关资料承接，不要求作者复制全文。

每轮只处理作者当前问题。可直接提问，也可说“只把动机改成保护妹妹”“保留这段关系，再给我两个结局”“采用第二版，但保留第一版开篇”。系统保存对象上下文、保留项和尚未解决的分歧，使作者能够连续推进。切到另一个对象后，其讨论历史独立，但经授权的跨对象引用可回查。

用户界面只有自然动作：继续讨论、修改当前内容、比较版本、采纳选中修改、撤销本次修改。无需展示工具名、字段路径或状态机。一次局部修改默认只生成一个有针对性的结果；只有作者明确要比较或存在需要选择的重大取舍时才生成多个方案。

## 讨论 修改 与采纳

### 讨论

解释、比较、短例子和头脑风暴直接返回回答。聊天记录能保存和回查，但不会修改作品设定或推进阶段。答案中的新想法保持候选身份。

### 明确修改

作者明确授权、对象和范围清楚且可以回退的修改，直接进入宿主的范围检查与执行。修改工作草案不增加固定确认步骤。对正式对象的清晰定点修正，同样可以由这条授权生成有版本的变更；仍需通过相应来源、事实、模板和阶段检查。这需要新增宿主授权适配，将原话和具体范围绑定为现有审批入口可接受的证据；当前 commit 对正式候选的 approvalId 要求继续生效，不通过删除审批检查实现低打扰。

“直接改”应绑定当前对象、选区、版本和本轮原话。模型只能提出变更，不能自行制造授权。宿主从作者原消息或界面操作建立 authorization，收到输出后核对实际变化是否落在授权范围。无法可靠确定目标时才询问一个必要问题。

### 需要审阅的变更

跨对象改写、影响范围未定、互斥创作路线、追溯改写已发生剧情或会破坏既有依赖的方案，先生成完整可比较差异和具体影响。用户的确认是执行前最后一步。已有明确授权覆盖的范围继续执行，不因工具实现细节重复索要确认。

“就按这个定稿”绑定当前可见候选及版本；点击按钮与明确自然语言采纳可以落到同一个宿主命令。候选发生变化后不能复用旧授权。正式正文仍进入原有正文与审核要求，不通过聊天绕过质量门槛。

## 同一事实只保存一次

对象层是现有文档、实体、关系与事实记录的版本化索引和视图，SQLite 继续是权威来源。卡片、图谱、时间线、表单和 Markdown 编辑器读取同一个对象版本。界面写入先形成变更，再由现有事务与物化机制同步文档。

现有文档没有稳定对象锚点时，第一步建立 documentId、sectionId 和可选 entityId 的映射；保留原文件路径与标题。字段结构尚未适配的对象继续使用原文档和文本差异，不宣称可以安全字段合并。解析不确定时显示待映射，不从标签或标题猜测并覆盖正文。

| 内容类别 | 可如何改变 | 不允许的混用 |
| --- | --- | --- |
| 已发生正文事实 | 正式修订产生新版本和影响记录 | 未来计划直接覆盖历史 |
| 已确认设定 | 定点修订或新的有效范围 | 将讨论建议自动转为设定 |
| 未来计划 | 调整未发生的安排并检查依赖 | 记忆提取把计划当成发生 |
| 讨论和候选 | 随作者意图反复比较与修改 | 被下游当成唯一正史 |
| 人物认知 | 保留知情人、依据及适用时间 | 用人物误解改写世界事实 |

## 锁定要求仍由作者掌控

锁定项保护作者原意，不是永久限制作者改变创意。作者后来明确要求改变某个锁定项时，新增一条有来源的约束修订，记录旧值、新值、来源消息和有效范围，再更新锁定状态。未经授权的其他锁定项继续保留。

例如先锁定“主角不知道父亲身份”，后来要求“从第十章开始知道”：保留前九章的知情状态，第十章起增加获取信息的来源和新状态。若作者改为“主角从开篇就知道”，这是追溯修订，先列出受影响的章纲、正文、对白、秘密关系和记忆，不把所有旧状态直接改成新值。

## 分支与局部采纳

创作分支保存共同基线和候选差异，只在当前分支预览。默认使用主线；作者明确比较不同选择时才创建分支。每个分支记录独立的假设与决策，切换分支不写入正式内容。

差异按可以独立成立的变更组提交。相互依赖的规则、代价和事件属于一个组，或有明确前置组。宿主检查字段合法性与引用，并计算依赖闭包。依赖闭包用于检查是否完整，不能自动采纳作者未选或未授权的组。已生效的前置可以满足依赖；其余情况请作者选择完整组合，或提出能够独立成立的修改。对语义依赖的判定保留证据和不确定性，不能声称程序已穷尽一切剧情影响。

作者可以只采纳角色动机，不采纳模型新增的身份；若身份正是动机成立的必要条件，则把依赖显示出来并要求选择一个完整方案。采纳后重新验证组合结果，不能只验证每个片段曾经各自成立。

版本比较显示共同点、实际变化和影响，内容来自同一基线上的对象差异。角色改名保持同一 entityId，关系和状态不因显示名称变化而复制成新角色。分支合并后保存原记录，撤销生成反向 changeset，并以当前版本和下游影响重新检查，不删除历史回执。

## 版本冲突与影响传播

每个请求绑定项目、对象、分支、来源版本和授权。AI 运行期间作者修改同一字段，旧结果进入待合并；不能覆盖较新内容。不相交字段只有在没有结构和语义依赖、且全部约束仍成立时才允许自动合并。若项目快照因无关改动前进，宿主先复核本轮 read set 与授权，再记录 validatedAgainstSnapshotId 并对当前快照提交；保留原始基线及验证记录。仍有疑问时显示具体冲突，不让整本书无关资料变动导致所有讨论同时失效。

影响分析由模型的候选说明与宿主依赖图共同组成。确定的引用、模板、来源和哈希依赖由程序计算；剧情因果影响是有依据的建议。上游设定改变后，相关计划、审稿记录、记忆候选或可视化投影分别标记待核对。仅刷新视图不需要模型调用。

已采纳内容不因一次讨论自动重写。作者可以选择仅调整未来安排，或明确授权追溯修订。新正文生成前，宿主阻止使用已失效的相关资料；没有受影响的章节继续正常使用。

## 统一输出合同

共创编辑只有两类模型输出。chat 提供自然语言回答和有效来源；proposal 提供回复、变更原子、依赖组、影响建议与必要决策。apply 是宿主命令，模型没有直接调用它的权限，也不填写授权、提交状态、审核通过或正式版本。对已显示候选的采纳、版本比较中的纯差异渲染、撤销和面板刷新可以本地完成；普通操作不为了总结或确认再调用模型。

与本设计配套的 vnext/co-creation-contracts.ts 定义对象引用、分支、授权、输入、输出、变更与应用回执。它是数据合同草案，仍需 JSON Schema、运行时验证器、工具适配和持久化迁移。模型输出中的 localId 只用于本次引用，正式 ID 由宿主分配；字段路径必须来自对象 schema 白名单，不能转成任意文件路径。

对象编辑仍经过对应业务合同。修改创意方向或其 assumptions 时，先合回原方向批次，再复用 DirectionReportV2 的恰好三案、稳定 ID、冻结内容、共享设定投影与引用检查。作者显式改变共享规则时，授权范围须明确覆盖所有受影响方向；仅修改所选方案的后续分支时，历史方向报告保持原版本。通用字段编辑不能绕过方向、命名、正文或记忆各自的专用验证器。

预检查依次验证当前版本、授权范围、锁定项修订依据、字段类型、原文锚点、引用及依赖；业务复核确认变更符合作者意图；正式应用沿用现有事务、幂等操作和回滚记录。收到成功回执后才显示“已更新”。网络结果未知沿用原恢复机制，不因聊天重复发送而创建重复改写。

## 接入顺序

第一批扩展 Conversation 与 run.discuss 的对象绑定，复用 candidateEdit 与 propose_action 的已有能力；增加统一对象入口和差异预览。

第二批完成角色、世界规则、章纲和场景的稳定锚点与字段适配；增加依赖组、局部采纳、范围授权和版本冲突处理。

第三批接入分支比较、有效章节范围和影响传播；再让角色卡、关系图、时间线和状态面板订阅同一对象投影。先保持原模板可往返，再逐步启用结构化编辑。

## 验收场景

1. 作者询问角色动机，正式资料和阶段不变。
2. 作者要求修改当前未采纳候选，正常完成且不重复索要授权。
3. 作者明确改变此前锁定的设定，保存约束新版本与原话，其他锁定项不变。
4. 仅选择一组修改时，独立内容保留；存在依赖时显示具体依赖并校验组合。
5. AI 返回期间同字段被作者修改，旧结果不能覆盖新版本。
6. 第十章起的状态变化保留前九章视图，人物认知与客观事实独立。
7. 修改世界规则后只标记相关下游资料，未授权的正文不被批量改写。
8. 同一操作重复提交返回已有回执，卡片、图谱、文档最终呈现同一版本。
9. 分支中的新增身份在合并前只属于该分支，另一分支和正式事实不受污染。
10. 撤销已应用修改生成可审计的新版本，并再次检查后续依赖。
