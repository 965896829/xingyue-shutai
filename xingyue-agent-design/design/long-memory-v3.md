# 百万字长篇记忆设计 V3

## 1 本轮核心建议

把百万字长篇记忆和人物动态心智提升为下一阶段的第一优先级。继续使用现有 TypeScript、SQLite、Pi、来源校验、候选与采纳体系，在其上完成按章增量更新、按对象索引查询、人物独立信念、章内状态转移和修订重放。共创讨论、角色卡、关系图与正文写作统一读取这套有版本的作品状态。

建议采用的主线是：已确认来源和事件保存完整历史，程序维护当前状态与检索索引，模型每次只获得当前场景需要的证据。每章实际出场角色都产生覆盖记录；有依据的变化形成增量，未发生或无法判断的变化明确保留其状态。

本轮核验的 main 仍为 0.4.82，提交 b505f6f459db74871f39f63acf6106b827c8a353。V3 是优化方案版本。上一版的作者意图保护、持续讨论、局部修改、高辨识度创意和真人化文风继续保留；开发顺序调整为记忆事务和上下文编译优先。[C01]

## 2 当前项目的基础和长篇瓶颈

项目已具备事实来源的路径、hash、引文和码点范围，也有事件、计划、信念、推断等分类，以及章节范围、揭示位置、人物知情和历史快照。现有记忆专项已要求处理本章出场或变化人物，模板包含情绪、原因、行为和下次承接。V3 应把这些已有文字约定升级为可验证合同。[MC01][MC03][MC14][MC15]

现有程序还具有 FTS、可选 embedding、预算裁剪、独立记忆审核、正文与记忆同版本绑定、审批事务、outbox 和增量快照。新的实现应复用这些边界。[MC05][MC07][MC09][MC10][MC11]

| 实际路径 | 当前观察 | V3 改动 |
| --- | --- | --- |
| 章后记忆输入 | runner 把累计台账全文作为必需资料装入 | 本章正文和相关状态输入，提交结构化增量 |
| 事实查询 | facts() 全量读取并反序列化，多处再筛选 | 查询列和复合索引先缩小范围，再加载数据 |
| 正式保存 | 重解析全部台账并整体替换 facts | 复用原事务，增量写入事实版本和投影 |
| 来源验证 | 相同原文可能反复读取和转为码点数组 | 按内容 hash 缓存引文验证，仍核对当前版本 |
| 向量检索 | 批次遍历向量并在 JS 计算相似度 | 增量批量 embedding，可替换原生向量后端 |
| 人物误信 | 知情标签不能完整表达人物实际相信的命题 | 独立信念、获知事件、修正与撤回区间 |
| 历史状态 | 正常结束和纠错均可能使用 superseded | 故事有效区间与编辑撤回分别保存 |
| 人物更新 | 模板提出要求，缺少逐角色覆盖合同 | 正文名单、维度覆盖、章内事件和稀疏变化 |

上述结论来自固定源码：runner 的全台账输入在 1156—1166 行；storage 的全量事实操作与提交重解析在 339—348、807—825 行；memory-studio 的全量筛选和来源检查在 25—157 行；embeddings 的向量遍历在 347—357 行。[MC04][MC05][MC06][MC07]

其中一个需要单独修正的语义问题是：正常状态演变会结束旧事实的章节区间，并把它标为 superseded；当前记忆视图又会排除 superseded。因此在当前版本回看较早章节时，可能看不到本应在当时成立的旧状态。历史 snapshot 能恢复旧版资料，但不能替代当前正史下的任意章节查询。此处是代码路径推导，需用专项回归用例验证。[MC04][MC13]

## 4 百万字记忆的分层结构

### 4.1 保留完整来源

已采纳正文、已确认设定和作者修订决定保留不可变版本。来源记录指向现有文档与 snapshot，不重新建立一份独立正史。原文包含的叙述、台词、梦境、转述与人物内心仍需分类；采纳正文不等于每句台词的内容都客观为真。

### 4.2 保存有依据的事件与状态

结构化记录包括世界规则、事件、人物目标、地点与资源、关系、人物信念和未兑现承诺。每条记录指向来源版本和具体位置。复杂因果使用共享事件引用，避免给每个角色复制一份完整正文。

人物说谎时，发言本身是已发生事件，发言命题可以是假的。人物相信一件错事时，确定的是他持有这个信念，信念内容不自动升级为世界真相。行为推断单独进入待确认观察。

### 4.3 维护可重建状态

角色卡、当前地点、关系图、开放承诺和章末状态由有效事件生成。它们带有版本和处理水位，点击后可以回到依据。现有 delta-v1 编辑快照继续使用；新增的是按对象和叙述位置加速查询的投影检查点。[MC10]

### 4.4 用摘要组织信息

场景、章节、分卷摘要用于导航、检索和压缩。摘要保留所依据的事件与来源，不靠反复压缩旧摘要来保存唯一记忆。关键物品位置、身份、承诺和世界规则直接查询结构化记录，不能因为久未出现而被摘要遗漏。

### 4.5 建立多种索引

精确实体和别名索引处理人名、物品和规则；全文索引处理原句和词组；向量补充不同措辞的召回；因果、关系和承诺索引处理跨章联系。索引和摘要可以重建，原文与已确认历史保留。

### 4.6 编译当前场景的记忆包

写作时只装入当前对象、必要事实、相关人物状态、知情边界、近期承接和需要兑现的旧线索。作品增长会扩大可搜索资料，但常规写作输入由当前任务预算控制。

## 5 时间 版本与人物知情

必须明确四种时间或顺序：故事发生的时刻、读者看到它的章节与场景位置、人物获得信息的事件，以及作者编辑与系统记录的版本。

故事时间允许相对先后和未知，不要求为所有事件编出日期。叙述位置使用稳定 chapterId、sceneId 和事件序号；显示章号来自版本内排序，拖动章节后不能继续把旧序号当作稳定身份。

| 查询需求 | 应当使用的范围 |
| --- | --- |
| 按今天确认的正史回看第 20 章 | 当前编辑版本，加第 20 章叙述边界 |
| 查看昨天那版作品的第 20 章 | 指定历史编辑版本，再加章节边界 |
| 问角色当时相信什么 | 对应人物信念及获知范围 |
| 查看作者尚未揭示的真相 | 作者范围，仍保留揭示限制 |
| 比较另一个候选分支 | 该分支及固定继承版本 |

编辑分支与作品中的平行世界、时间线是不同字段。候选分支继承创建时的父版本；父分支后来变化不能自动混入候选。合并通过明确变更与冲突处理完成。

正常成长、受伤和痊愈用有效区间表达；作者删改旧章用编辑撤回与新来源表达。记录仍可保留，是否能作为当前证据由查询范围决定。新别名和秘密身份也受揭示与人物知情限制，不能因为内部实体已经合并就把新身份泄漏到早期对白。

## 6 下一章怎样取到正确记忆

### 6.1 先确定本章必需内容

宿主从场景合同取得人物、地点、物品、规则、时间和相关承诺。先直接查询硬约束、当前有效状态和本章要用的未结事项。第 3 章建立且至今有效的事实，与最近发生的事实同样可以成为必需项。

### 6.2 在合法范围内并行召回

对实体、全文、语义和有界关系路径分别查询，先限制项目、编辑分支、版本、来源有效性、叙述范围和用途。召回后再次检查来源及使用范围。排名合并可以采用 RRF；初期限制展开深度与候选数，是否重排以实际质量和延迟比较决定。[MR27]

先过滤时，向量后端如果不支持全部条件，可先取得允许集合再精确搜索，或受限地增加候选并过滤。过滤后没有足够证据就报告缺口，不能用不合范围的结果补齐。人物视角中的原文片段也必须检查是否夹带旁白真相或其他人的秘密；必要时只提供该人物有依据的命题和可见片段。

### 6.3 保留因果与长期承诺

“她为什么拒绝曾经帮助过她的人”需要当前决定、过去事件、关系变化和未解决目标。查询不应只取相似段落。长期伏笔和承诺有独立开放索引，按本章关联与预期窗口选入；过期未兑现显示为创作待办，不由程序自动宣布完成。

### 6.4 处理完整清单问题

“截至第 200 章所有未兑现承诺有哪些”属于结构化全量查询，应使用分页与固定快照。向量 top-k 不适合证明“所有”。输出若受长度限制，返回明确的后续游标和统计，不把前几项冒充完整答案。

### 6.5 形成可检查的工作包

工作包包含任务范围、必需事实、角色入场状态与信念、有关事件和承诺、来源引用、尚未解决的冲突以及索引水位。作者资料、未来计划、写作控制信息与已发生事实分别标明。写作可以参考已批准的未来计划，但不能把计划当作已经发生的状态。

常规记忆包建议以 8,000 token 为初始可调预算，先在 4,000、8,000、12,000 三档比较。此数值是工程实验起点，包含记忆资料而不等于完整模型请求；总控、工具定义、场景、文风和输出余量另计。使用实际模型 tokenizer 或供应商计数，不能按中文字数固定换算。[MC08]

必需项预算不足时，宿主应增加预算、分场景处理或给出具体缺口，不能静默丢弃硬约束。复杂查询允许一次有预算的补检索，避免没有上限的自主搜索循环。

## 7 章后增量记忆事务

保持现有正文候选、记忆候选、独立审核和采纳边界。正常链路仍可在正文候选确定后提取增量，等作者采纳相同 hash 的正文时一同正式提交；不因增加人物功能再做一遍同样提取。[MC06][MC11]

建议流程：编译入场状态，生成或编辑正文，固定正文 hash，生成实际人物名单，批量提取本章事件与状态变化，执行本地结构和来源检查，复用独立语义审核，随后在采纳事务中发布正式版本及投影更新任务。

幂等标识绑定项目、分支、章节 ID、正文 hash、读集摘要及抽取合同版本。同键同产物复用，同键不同内容拒绝覆盖。读集摘要包含影响输出的状态、来源、模型与提示词版本；发布前再次核对，过期结果不能落入新版本。

正文、已验证增量与发布状态使用原有事务及 outbox。状态、信念和覆盖这些下一章必需数据应达到同一有效水位；embedding、普通摘要和次要图形索引可以后台更新。核心记忆待同步时，界面清楚显示受影响范围，只等待依赖该范围的自动写作，无关编辑继续进行。

台账与角色卡由权威结构物化。作者编辑台账时，应通过现有共创或资料编辑入口形成有来源的变更；派生台账不能再被当作独立原始证据重复抽取，否则同一推断会在反复导出导入中被放大。

## 8 修改旧章后的恢复

旧章修订同时涉及检索索引和故事因果。删除一段话后，先撤回旧来源版本的使用资格，失效相关事实、信念、摘要和投影；再从合适的检查点重放有效事件。依赖原解释的抽取可能需要重新提取，不能假定只回放旧 delta 就一定正确。

依赖记录包含读过的具体记录，也包含查询范围和查询不到结果这一条件。例如，某场戏建立在“他从未见过这封信”上，作者新增一次早期见信事件时，原先的空查询同样应失效。仅记录返回过的事实 ID 会漏掉这种影响。

空查询只表示在指定来源、范围和索引水位内没有找到记录。范围不完整、向量只取了前几项、索引尚未完成时，不能据此断言从未发生。否定性的故事事实仍需要作者、正文或范围完整性的依据。

对历史项目无法证明依赖完整的部分，继续使用较宽的待核对范围。只有依赖覆盖完整时，才把无关对象排除。后续已采纳正文只标记潜在矛盾或待复核，修改正文仍走作者授权流程。

缓存键包含项目、分支、编辑版本、叙述边界、人物视角、来源 hash、结构版本和编译器版本。引文验证缓存可以复用不可变原文的结果，但每次仍需判断该来源在当前版本是否有效。

## 16 百万字规模与效率

以每章 2,500 个中文正文 Unicode 码点计算，一百万码点约 400 章；此处包括标点、数字等。实际字数、Unicode 码点、token、场景数、事实数和向量数分别计量。一个作品有百万字，不代表要保存百万个向量。

按当前分块上限估算，百万字正文的向量块通常是数千级这一量级，实际取决于段落与切片。先消除全表反序列化、重复读文件和逐块远程请求，再按真实向量数决定原生精确检索还是 ANN。SQLite 官方已有 vec1 路线；可把向量实现做成适配器，固定版本后比较召回、延迟和安装包成本。[MC07][MR23][MR24]

中文人名需要精确别名索引。FTS5 的 trigram 全文查询不能匹配不足三个 Unicode 字符的子串，常见二字姓名不能仅依赖这条路线。应测试分词、字粒度检索、同名、简称和别名，并对结果执行相同的版本及知情检查。[MR26]

章后一次批量提取同时处理人物和事件，复用已有独立审核；调用次数不按全书角色数增长。embedding 仅处理变化片段，在服务商限制内批量执行。投影刷新、图形显示、精确查询、版本校验、缓存和回放都由程序完成。

常用人物卡和未结承诺预计算；缓存键有版本。后台任务持久化、可取消、有预算，原模型请求结果未知时遵循现有恢复策略。核心数据优先就绪，向量和摘要的水位独立显示，避免为了等所有附属索引阻塞作者阅读。
